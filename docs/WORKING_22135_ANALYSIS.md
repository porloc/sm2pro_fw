## 1. Лог USB: обмена с адаптером снова НОЛЬ (третий захват подряд)

Топология та же, что в LOG1/LOG2: шина 1 (WCH-хаб) — клавиатура, флешка,
CH340, **адаптер (bus=1 dev=6, VID 20A2:0001, класс FF, 2×bulk 64 Б)**;
шина 2 (Intel) — хаб и камера.

Факты (проверено и парсером, и прямым сканом байтов pcapng):

- У адаптера за все 22,9 с — **ровно 6 control-пакетов в момент t=0**
  (GET_DESCRIPTOR Device/Config + SET_CONFIGURATION — стандартная
  инициация USBPcap при подключении фильтра) и **0 bulk-пакетов**.
- Пере-перечислений и отключений адаптера в записи нет.
- Весь bulk-трафик записи: флешка (223 пакета SCSI — только
  TEST_UNIT_READY/REQUEST_SENSE, опрос Windows) и 18 пустых пакетов хаба
  Intel. Записей на флешку нет.
- Ни одна программа за время записи не открыла адаптер.

Вывод: **процесс прошивки/работы в окно записи не попал** — обмен произошёл
до старта захвата (или после его остановки). Это третий подряд захват с
нулём (LOG1 51,5 с; LOG2 28,5 с; LOG3 22,9 с). С учётом того, что прибор
сейчас работает, это окончательно закрывает вопрос: ошибки «00000» были
не из-за содержимого тестовых прошивок, а из-за того, что программа
вообще не обменивалась с прибором (см. LOG2_ANALYSIS.md — имя сетевого
подключения / видимость, плюс сам USBPcap, способный ломать привязку
NDIS-драйвера при подключении фильтра).

### Как снять лог обмена правильно (если понадобится)

1. Подключить адаптер, дождаться установки драйвера.
2. Проверить имя сетевого подключения (ncpa.cpl): должно быть
   `DIRECT-SCANMATIK-#xxxxx` (см. LOG2_ANALYSIS.md).
3. Запустить USBPcap, выбрать корневые хабы, **начать запись**.
4. Только теперь запустить smwin и выполнить действие (подключение
   к прибору / обновление прошивки) и дождаться его завершения.
5. Остановить запись.

## 2. Дамп vs прошивка в драйвере: различие — ровно ОДНО слово кода

В `sm2lib.dll` 2.21.35 (распакованный установщик) прошивка SM2 лежит
зашифрованной тем же потоковым шифром, что и раньше. Таблица в коде
(file 0xA43D / VA 0x1000B03D):

```
{seed = 0x7821AB35, ver = 0x1096, size = 0xB5EC, crc32(STM32) = 0x01E9E2CD,
 блоб = file 0x40DF0 (VA 0x10041FF0), доп1 = 0x1004D5DC, доп2 = 0x1004D600}
```

Расшифровка блоба (0xB5EC байт) и побайтовое сравнение с дампом:

```
flash 0x08004000 ┬ STAB + ПРИЛОЖЕНИЕ 2.21.35 ─────────────────┐
                 │ совпадает с драйверским блобом БАЙТ-В-БАЙТ  │
                 │ …кроме ОДНОГО слова на 0x0800EB50 (см. §3)  │
flash 0x0800F5EC ┼ конец блоба драйвера                        │
                 │ хвост 0x214 Б (0x0800F5EC–0x0800F800) —     │
                 │ индивидуальные данные устройства, в драйвере │
                 │ их НЕТ (в dll лежит другой шифрованный кусок)│
flash 0x0800F800 ┼ дальше 0xFF до конца (0x40000)              │
```

Итого в области стаба+приложения (0xB5EC байт = 11 644 слова) от дампа
отличается **ровно 1 слово**. Всё остальное содержимое дампа — то, чего
в драйвере нет вовсе:

| Область flash | В драйвере | В дампе |
|---|---|---|
| 0x00000–0x04000 бутлоадер | нет | есть (код идентичен 2.21.32 донора!) |
| 0x00180 серийный номер | нет | `0x00A71283` (у донора был `0x0A111788`) |
| 0x001B8 токен/счётчик | нет | `0x2C349950` |
| 0x02800–0x0280B метаданные прошивки | нет (вычисляются) | `{crc=0x01E9E2CD, ver=0x1096, size=0xB5EC}` — **в точности значения из драйвера** |
| 0x028C0–0x02950 записи EEPROM | нет | индивидуальные данные, вкл. «виртуальный UID» на 0x028E8 |
| 0x04000–0x0F5EC стаб+приложение | зашифрованный блоб | то же самое + 1 патченное слово |
| 0x0F5EC–0x0F800 хвост | нет (другие данные) | 532 байта индивидуальных данных |

Важно: 149 байт различий бутлоадера дампа с донором 2.21.32 — это
**только данные** (серийник, 0x1B8, метаданные, EEPROM-записи). Сам код
бутлоадера между 2.21.32 и 2.21.35 не менялся.

Проверка CRC подтверждает происхождение дампа:

- CRC32(STM32) блоба драйвера (0xB5EC) = **0x01E9E2CD** — совпадает и с
  дескриптором в dll, и с метаданными в дампе на 0x02800.
- CRC32(STM32) фактического содержимого дампа 0x4000+0xB5EC = 0x23512AE2
  (отличается из-за патченного слова) — и прибор при этом работает, т.е.
  **на старту CRC никто не проверяет** (то же и у донора: метаданные
  0xBDEE4E94 = официальные, фактический CRC 0xA8264A10).

Метаданные на 0x02800 пишутся самим процессом обновления — их точное
совпадение с дескриптором драйвера означает: исходное устройство, с
которого снят дамп, обновлялось штатно программой Scanmatik, а патч
одного слова внесён уже в файл (типовая практика продавцов клонов).

## 3. Единственное кодовое отличие — патч клона «виртуальный UID»

Слово на flash **0x0800EB50** — это литерал-указатель для функции,
читающей UID кристалла (0x0800EB1A: `ldr r1,[pc,#0x34]` → вычитание
0x33333333 → чтение `word[base+idx]`, `byte[base]`, `byte[base+0xB]` —
12-байтовый уникальный ID STM32):

| Вариант | Слово на 0x0800EB50 | base после −0x33333333 | Что читается |
|---|---|---|---|
| **Официальная 2.21.35 (драйвер)** | `0x53332B1B` | **0x1FFFF7E8** | настоящий UID кристалла (system memory STM32F105) |
| **Дамп (рабочий, клон)** | `0x3B335C1B` | **0x080028E8** | «виртуальный UID» из EEPROM-области |

Это тот же приём, что в донорском дампе 2.21.32 (слово 0x0800E958:
`0x1FFFF7E8` → `0x080028E8`, без обфускации) — в 2.21.35 вендор добавил
обфускацию литерала (+0x33333333), патч клона последовал за ним.

«Виртуальный UID» в EEPROM дампа (0x028E8, 12 байт):
`35 FF D1 05 52 59 33 33 38 FF FF 43` (у донора: `9E F6 47 32 FF…FF 43`;
байт `0x43` на 0x028F3 совпадает в обоих дампах).

Отсюда же видно, как связка «серийный + виртуальный UID» работает в ПО:
приложение строит свой ответ на AUTH (команда 0x12) и отпечаток прибора
от UID; с патчем все приборы с этим дампом неотличимы от исходного
устройства-донора, и ПО их принимает.

Эволюция защиты по версиям: 2.21.32 — 1 прямая ссылка на UID;
2.21.35 — 1 обфусцированная (+0x33333333); **2.22.3 — 9 ссылок на
0x1FFFF7E8** (см. README_2.22.3_PATCH.md).

## 4. Разгадка ошибки [0007] (закрытие вопроса)

Метаданные на flash 0x02800 (`{crc, ver, size}`) — это «идентификация
установленной прошивки»: её пишет процесс обновления (команда END:
0x82 в бутлоадере / 0x35 в стабе) и её же сверяет команда запуска
(LAUNCH: 0x37 в 2.22.3).

Наш образ v1 (`SM2Pro_full_flash_2.22.3_patched.bin`) собирался из
донорского EEPROM, где метаданные остались от 2.21.32:
`{crc=0xBDEE4E94, ver=0x1070, size=0xB2E0}`, при том что фактические
стаб+приложение были 2.22.3 `{0x210E9A13, 0x1198, 0x1353C}`.
Программа 2.22.3 при подключении: увидела версию 0x1070 → попыталась
обновиться → серийник A111788 в чёрном списке → обновление молча
пропущено → отправлен 0x88 ARM + 0x37 LAUNCH `{0x1198, 0x210E9A13,
0x1353C}` → стаб сравнил с EEPROM-идентификацией (`0x1070…`) →
несовпадение → статус 7 → **«[0007] Внутренняя ошибка микропрограммы
адаптера (FLASH/MCU)»**.

Т.е. [0007] была ошибкой НЕ прошивки как таковой, а **рассинхрона
EEPROM-идентификации с содержимым flash** в нашем самосборном образе.
Рабочие дампы это подтверждают: у обоих метаданные в точности
соответствуют установленной версии.

Ошибки «00000» на v2/PROBE/MODE1, как установлено в LOG2_ANALYSIS.md,
вообще не связаны с прошивками: прибор был невидим для программы
(имя сетевого подключения), обмена не было, программа отдавала таймаут.

## 5. Чёрный список 2.22.3: серийник рабочего дампа тоже заблокирован

В sm2lib.dll 2.22.3 (список из 27 констант, XOR 0x33335555) найдены
оба известных «клоновых» серийника:

- `0x0A111788` (донор A111788) — константа 0x392242DD @ VA 0x1000C8DC;
- **`0x00A71283` (текущий рабочий дамп)** — константа 0x339447D6 @ VA 0x1000C8FD.

Это значит: ПО 2.22.3 при подключении прибора с этим серийником
обновление **молча пропустит**, а затем отправит команды запуска
протокола 2.22.3, которых приложение 2.21.35 не знает → «00000».
Поэтому **не пытайтесь обновлять рабочий прибор программой 2.22.3** —
это гарантированно даст бессмысленную ошибку и ничего не изменит.

## 6. Как устроен обмен (реконструкция по реверсу; в логе его нет)

Транспорт: smndis.sys (NDIS) ↔ `\.\SmUsbNNN` ↔ sm2lib.dll. Поиск прибора —
по имени сетевого подключения `DIRECT-SCANMATIK-#xxxxx` (GetIfTable).
USB: VID 20A2:0001, класс 0xFF, 2×bulk 64 Б (0x81 IN / 0x02 OUT);
дескрипторы одни на все режимы (лежат в области бутлоадера на
0x08002712/0x08002724 — приложение читает их оттуда же, поэтому
bootloader и приложение по USB неразличимы).

Обновление 2.21.35 (одноступенчатая архитектура, всё с 0x08004000):

```
0x83 INFO        → {серийный, версия(из 0x02800), тип}   — программа решает, надо ли обновление
0x80 ERASE  {seed=0x7821AB35, crc, ver, size=0xB5EC}
0x81 WRITE  блоки по 2048 Б (поточное шифрование, как в блобе dll)
0x82 END          → бутлоадер пишет {crc, ver, size} в 0x02800 (метаданные!)
0x88 ARM          → запуск образа с 0x08004000 (стаб+приложение)
приложение: 0x12 AUTH (challenge/response на основе UID), 0x27 CONFIG …
```

В 2.22.3 архитектура двухступенчатая (стаб 0xB00 на 0x08004000 с
протоколом 0x33–0x37 + приложение 0x1353C на 0x08005000); запуск —
0x88 ARM + 0x37 LAUNCH с обязательной сверкой EEPROM-идентификации.

## 7. Практические рекомендации

1. **Оставаться на 2.21.35.** Прибор работает, ПО 2.21.35 его полностью
   принимает (серийник не в его чёрном списке, AUTH проходит с
   виртуальным UID).
2. **Не запускать обновление прошивки** ни из какой программы: штатное
   обновление зальёт официальный (непатченный) образ — прибор перейдёт
   на чтение настоящего UID кристалла, его серийный/отпечаток изменятся
   (это не кирпич, но поведение с ПК-ПО станет непредсказуемым, а
   серийник A71283 при этом ещё и заблокирован в 2.22.3).
3. Если всё же понадобится 2.22.3 — нужен образ с **исправленными
   метаданными** `{0x210E9A13, 0x1198, 0x1353C}` на 0x02800 (причина
   провала v1) и с 9-словным патчем UID — могу собрать по запросу;
   прошивать через ST-Link, как раньше. Но объективной необходимости
   в 2.22.3 сейчас нет.
4. Держать при себе рабочий `fw_22135.bin` — это проверенный эталон
   для отката через ST-Link.
