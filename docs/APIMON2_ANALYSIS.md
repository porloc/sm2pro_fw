# API Monitor захват №2: сессия smwin 2.22.3 ↔ прибор (прошивка 2.22.3, образ v2)

Дата: 19.11. Файл `capture2.apmx86` (2,17 МБ, 44 вызова) по ссылке Google Drive.
Прибор: клон, прошит `SM2Pro_full_flash_2.22.3_patched_v2.bin` (EEPROM-фикс v2).
ПО: `C:\Program Files (x86)\Scanmatik\smwin.exe` 2.22.3 (Sm2Lib, PlxLib, IPHLPAPI).

## Формат .apmx86 (дополнение к разбору №1)

- `calls` = массив u32-смещений записей в `data` (44 шт.).
- Заголовок записи: `@+0x10` — не таймер (константа сессии); `@+0x38` — u64 QPC,
  1 ед. = 100 нс (калибровка по старому захвату: 117383369 ед. = 11,74 с).
- `@+0x40` = возвращаемое значение (BOOL DeviceIoControl), `@+0x44` = GetLastError.
- Пул 0x0800017C в приложении = адрес диспетчера сервисов бутлоадера 0x080002CD
  (вызов: r0 = код сервиса → blx).

## Что это доказывает

1. **EEPROM-фикс v2 полностью работает.** INFO честно отвечает версию 0x1198
   (загрузочная запись 0x2800), [0007] мёртв. Серийный A111788 в чёрном списке
   2.22.3 не мешает: версия совпала → обновление не запускается вовсе.
2. **Стадия запуска работает идеально**: ARM OK; LAUNCH 0x37 с параметрами
   {0x1198, 0x210E9A13, 0x1353C} (в точности значения из sm2lib.dll 2.22.3,
   как предсказано) принят стабом — сверки слотов 3–8 прошли, статус 0,
   приложение запущено.
3. **Отказ ровно один: приложение 2.22.3, запустившись, не отвечает.**
   На AUTH (новый формат: challenge 172Б вместо 10Б) драйвер ждёт ~1,4 с,
   получает ничего, возвращает GEN_FAILURE. Это и есть «Внутренняя ошибка
   микропрограммы 00000» на экране.

Транспорт (бутлоадер-USB + сервисы + smndis + smwin) исправен — ответ на 0x37
прошёл тем же путём за миллисекунды до отказа. Сломано внутри приложения.

## Статический разбор пути AUTH в приложении (новое)

Диспетчерская таблица команд (12Б/запись, @0x0800C06C): `0x12 → 0x0800722D`,
`0x27 → 0x08007E61` (CONFIG — чтение/запись EEPROM-слотов 0x38–0xB8).

Обработчик AUTH 0x0800722C:
```
ldrh [packet+1] == 0xAC (172) — проверка длины challenge   ✓ ПК шлёт 0xAC
svc 7  (серийный)                → [sp+0x58]
svc 8  (ключ по индексу, из крипто-блоба бутлоадера 0x08000184) ×2  → [sp+0x5C],[sp+0x60]
bl 0x0800C15C — крипто-ядро (обфусцировано, читает UID через пул 0x0800C520)
cbz r0 → построение и отправка ответа; иначе статус 6
```
Все входы ядра на месте (блоб 0x08000184 и виртуальный UID 0x080028E8 —
донорские, в образе). Значит входы не проблема — либо диспетчер приложения
не доходит до 0x12 (смерть на init), либо зависает само ядро 0x0800C15C.

Команда 0x27 CONFIG (0x08007E60): type 0 — чтение 128 слотов 0x39–0xB8
(адреса 0x080028BA–0x080029F0) в ответ; type 0x99 — запись с проверкой
(svc6). Для подключения не используется (в трейсе её нет, и не надо).

## USBPcap: закрыть вопрос

USBPcap больше НЕ НУЖЕН: API Monitor покрывает протокол полностью (обе сессии
расшифрованы до байтов), а USBPcap на этой машине даёт ноль bulk-пакетов при
живом обмене (доказано этим захватом) и, подключая фильтры, ломает привязку
smndis (имя DIRECT-…, причина «00000» в LOG2). Не тратить на него время.
