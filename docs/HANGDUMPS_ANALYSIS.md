# Разбор дампов зависания (прогоны A и B через J-Link OB)

Дата: 21.11. Источник: `testA_hang_dump_log.txt` + `testA_hang_ram.bin` (прошивка
`patched_v2`, ожидание «00000») и `testB_*` (`AUTH_BYPASS`, ошибка «54А14094»).
Снято J-Link OB (Blue Pill), J-Link V9.96, STM32F105VC, SWD 1000 кГц.

Важная особенность снятия: в обоих логах первая попытка подключения провалилась
(`Failed to initialize DAP`), J-Link выполнил connect under reset — ядро
остановлено на векторе сброса (PC=0x0800032C, SP=0x20001800, LR=0xFFFFFFFF).
Точный PC зависания сброс уничтожил, **но SRAM при системном сбросе
сохраняется** — дампы RAM содержат состояние зависания. Анализ ниже — по RAM.

## Краткие выводы

| | Прогон A (patched_v2) | Прогон B (AUTH_BYPASS) |
|---|---|---|
| Крипто-ядро 0x0800C15C | **запускалось и ВЕРНУЛОСЬ** (кадр вытолкнут, VM-таблица заполнена) | не запускалось (патч) — VM-таблица 0xFF |
| Что произошло | ядро работает **секунды** (≈3–4 с), ответ AUTH приходит ПОСЛЕ таймаута драйвера (1,4 с); отправка ответа зависает в ожидании IN-endpoint (хост уже не читает) | ответ (мусор) отправлен мгновенно и принят ПК; ПК отправил 248Б верификации; **старый парсер бутлоадера не понимает 248Б** — приложение блокируется в svc 0 навсегда, USB умирает |
| Экранный итог | «00000» ×3 цикла | «Внутренняя ошибка микропрограммы 54А14094» |

**Общий корень: 2.22.3 рассчитана на новое поколение бутлоадера.** Ядро на
входах старого бутлоадера уходит в долгий путь (секунды вместо мс), а 248Б
сообщение верификации — сообщение НОВОГО протокола, которое старый парсер
пакетов не умеет разбирать.

## 1. Хронология прогона A (восстановлена по стеку)

1. INFO → ARM → LAUNCH → приложение запущено (стартовые кадры 0x2000FEC0+).
2. AUTH: обработчик 0x0800722C (кадр на 0x2000FD58–0x2000FED0, sp=0x2000FD58;
   серийник 0x0A111788 и ключи 0x58C43B00/0xA3566524 в локалах [sp+0x58..0x60]).
3. Вызов ядра `bl 0x0800C15C` — **ядро вернулось** (доказательства: сохранённый
   LR 0x08007293 в RAM отсутствует → push-кадр ядра не жив; VM-таблица
   0x2000D05C заполнена → вход ядра отработал; остатки кадра ядра с данными VM
   на 0x2000F948–0x2000FD34).
4. Путь успеха (копирование ответа): прерывание ударило в helper 0x08008944
   из цикла 5 (аппаратный кадр {lr=0x08007321, pc=0x08008944, xpsr=0x81000000}
   на 0x2000FD38–0x2000FD58 + `push {lr}`=0xFFFFFFF9 обработчика ниже) —
   нормальная работа.
5. AUTH вернулся в главный цикл (0x0800B9A6). Отправка ответа пошла через
   svc 3 (тик) → USB-поллинг → конечный автомат endpoint.
6. **Живая цепочка на стеке: 0x080011FD → 0x080018AD → 0x080014E9 → 0x08000CF7
   → bl 0x080009E6** — путь записи IN-endpoint (DIEPCTL 0x50000000+0x900 на
   стеке). Отправка ждала готовности endpoint (хост перестал читать — его read
   истёк по таймауту 1,4 с ещё пока работало ядро).
7. Приложение восстановилось (цикл svc0/svc3), ПК перезапустил цикл: 0x86 →
   INFO → ARM → LAUNCH (перехват v2-захвата: между циклами прибор ОТВЕЧАЕТ —
   cmd 0x80–0x8A обслуживаются таблицей бутлоадера внутри приёмника!). 3 цикла
   ≈ 5 с каждый → **ядро работает ≈3–4 секунды** (на эталонных входах обязано
   быть миллисекунды — иначе подлинник не прошёл бы таймаут 1,4 с).

## 2. Хронология прогона B (AUTH_BYPASS)

1. AUTH: ядро заменено на `movs r0,#0` → путь успеха с пустым буфером →
   ответ {статус 0, len 0x134} — 308 Б (первый 64-байтовый пакет захвачен).
   «Эхо challenge» в ответе объяснено кодом: data[40..43] = восстановленный
   ctx->[0x2C] (save/restore вокруг вызова ядра), data[44..47] = копия старого
   ctx->[0x30] — ядро действительно не работало.
2. ПК принял статус 0 → отправил 248Б верификации (28 нулей + серийник
   88 17 11 0A + слова крипто-блоба 00 3B C4 58 / 24 65 56 A3).
3. **Парсер пакетов бутлоадера (машина состояний 0x08002240+: [r4+0x12]=ожидаемая
   длина, [r4+0x14]=принято, чтение побайтово до полной длины) не понимает
   поток**: как поток старых пакетов {cmd,len,csum} это 7 пустых пакетов cmd 0
   с битыми контрольными суммами и «заголовок» {cmd 0x88, len 0x1117} из байтов
   серийника — парсер ждёт 4375 Б данных, которые никогда не придут.
   Живой кадр: 0x080010B3 (возврат в ядро приёма из 0x08001708) + 0x0800225F /
   0x080022E4 (внутри машины состояний) — **приложение заблокировано в svc 0**.
4. Главный цикл не крутится → svc 3 (тик/USB-поллинг) не вызывается → USB
   умирает → драйвер удаляет устройство (через 72 с CreateFileW на все
   SmUsb* = err 2 — прибор исчез физически). Ошибка «54А14094» = реакция ПК на
   невалидное тело ответа AUTH (код не является CRC32 захваченных 64 Б ответа
   или challenge — вычисляется от полного 308-байтового ответа/ключей сессии).

## 3. Архитектура (уточнена реверсом)

* Реальная таблица сервисов бутлоадера @0x08000328 (14 записей; диспетчер
  0x080002CC: `svc#(arg)`), svc[0]=0x0800122A приём, svc[1]=0x0800123A
  отправка, svc[3]=0x08001296 тик, svc[7]/svc[8] серийник/ключи, svc[13]
  регистрация.
* svc[0] = обёртка: `bl 0x080011F6 (USB-поллинг); bl 0x080010AA (ядро приёма)`.
* Ядро приёма: байт cmd 0x80–0x8A → таблица бутлоадера (INFO и др. answered
  здесь же, ответ отправляется `bl 0x08001784` из приёмника!); прочие команды →
  проверка состояния приложения (0x0800108E: состояние 3 = приложение
  зарегистрировано) → возврат указателя сообщения главному циклу приложения.
* Главный цикл приложения (0x0800B99E): таблица команд @0x0800BF68, записи
  {cmd, flg, handler}: 0x12→AUTH 0x0800722C, 0x27→0x08007E60, 0x37→0x08007F5C
  и т.д.; обработчики flg=0 вызываются трамплином из глубины svc-цепочки
  (сохранённый LR обработчика = 0x0800B9A7 — возврат прямо в главный цикл,
  регистры {r4=ret в svc[0], r5=0x0800017C, r6=0x080002E5, r7=0x080002CD}
  = живые регистры svc-цепочки).
* Отправка ответов идёт через USB-поллинг (svc 3 / обёртки svc) → конечный
  автомат endpoint 0x080009E6 (tbb по состоянию [X+0xA8], цикл состояний).

## 4. Проверка побочных гипотез

* **SWD отключает БУТЛОАДЕР — в момент LAUNCH** (найдено позже, реверсом
  `scripts/scan_debug_block2.py`, см. `docs/JLINK_OB_GUIDE.md` раздел 3а):
  единственная во всей прошивке запись AFIO_MAPR с SWJ_CFG=100 («JTAG-DP и
  SW-DP выключены») — функция 0x08000E14 (`bic #0x07000000; orr #0x04000000`),
  вызываемая ТОЛЬКО из блока запуска приложения (bl на 0x0800133C; вход —
  b.w 0x0800132A из обработчика 0x37 LAUNCH @0x080002A0). Приложение само
  SWJ_CFG не трогает (его ссылка на AFIO_MAPR, пул 0x08014918 — только ремап
  TIM/USART движка пинов J2534). Отсюда «Failed to initialize DAP» в обоих
  логах — НЕ флейк клона OB: оба дампа сняты у прибора в пост-LAUNCH
  состоянии (SWD мёртв), спас connect under reset (NRST). В простое
  бутлоадера (после перетыка питания, без smwin) SWD жив. Для отладки
  запущенного приложения собран образ `SM2Pro_full_flash_2.22.3_patched_v2_SWDON.bin`
  (SWJ_CFG=010: SWD остаётся включён после LAUNCH).
* **USB-состояние (0x200013C0–0x20001400) не повреждено** ядром: области в A и
  B идентичны; различия только в скретче ядра 0x20001400+ (A: данные VM —
  0xEC133738, 0x2000FD58, 0x20000360, 0x2B0D87D8, 0x48, 8; B: нули) и в
  счётчиках времени USB.
* Fault-кадров (HardFault/BusFault) на стеках нет — оба зависания = циклы
  ожидания, не крэши.

## 5. Решающий следующий шаг: бонус-прогон с брейкпоинтами

Цели: (1) измерить время работы ядра (подтверждение медленного пути),
(2) снять VM в середине работы (горячая точка цикла — для офлайн-декодирования
VM-программы), (3) зафиксировать возвращаемое ядром значение.

Полный алгоритм — `docs/JLINK_OB_GUIDE.md`, раздел 6 (обновлён под новые цели:
ловушки на входе 0x0800C15C, возврате 0x08007292 и остановка по таймеру в
середине работы ядра).

## 6. Практический вывод

Если бонус-прогон подтвердит, что ядро возвращает 0 (валидный ответ) за ~3–4 с —
единственный блокер на старом бутлоадере = скорость ядра; тогда следующий шаг —
декодирование VM-программы из дампов (таблица 0x2000D05C + кадр 0x2000F948+) и
поиск пути-тормоза (вероятнее всего — намеренная задержка/медленная ветка на
«чужих» входах). Если ядро возвращает 6 — ответ в принципе не собирается, и
2.22.3 на старом бутлоадере закрыта (нужно поколение нового бутлоадера, которого
в дистрибутиве нет — записи обновления бутлоадер не пишут).
