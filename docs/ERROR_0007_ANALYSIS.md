# Анализ и исправление ошибки [0007] «Внутренняя ошибка микропрограммы адаптера (FLASH/MCU)»

## Симптом

После заливки `SM2Pro_full_flash_2.22.3_patched.bin` (собран ранее: бутлоадер
2.21.32 донора + stub 2.22.3 + патченное приложение 2.22.3 с перенаправлением
чтения UID в EEPROM) родная ПК-программа Scanmatik при подключении адаптера
выдаёт:

```
[0007] Внутренняя ошибка микропрограммы адаптера (FLASH/MCU)
```

Устройство при этом живо: USB поднимается (VID 0x20A2 / PID 0x0001),
протокол отвечает.

## Откуда берётся текст ошибки

Строка «Device firmware internal error (FLASH/MCU)» / «Внутренняя ошибка
микропрограммы адаптера (FLASH/MCU)» найдена в `sm2ptconfig.exe` (UTF-16,
file 0x9B168/0x9B1C0) и в `plxlib.dll`. В `sm2ptconfig.exe` раскрыта таблица
ошибок: функция с `switch` по коду ошибки (jump-table на VA 0x41838C,
таблица строк-дескрипторов .rdata, переключение `jmp dword ptr [edi*4+0x41838C]`),
**код 7 → дескриптор 0x498350 → эта строка**. То есть **[0007] — это статус
устройства 7**, возвращённый по протоколу, который ПК показывает как
«внутреннюю ошибку микропрограммы».

## Кто возвращает статус 7

### Загрузчик-стаб 2.22.3 (0x08004000), команда запуска 0x37

Дизассемблирование stub'а (диспетчер 0x08004240, `tbb` на команды 0x33–0x37):

| Команда | Обработчик | Назначение |
|---------|-----------|------------|
| 0x33 | 0x0800425A | ERASE приложения (с 0x08005000), приём параметров {seed, crc, ver, size} |
| 0x34 | 0x080042FC | WRITE блоков 0x800 (поточное дешифрование) |
| 0x35 | 0x080043A4 | END: проверка CRC32 приложения (сервис бутлоадера, опкод 9) и **запись {crc, ver, size} в EEPROM-слоты 3–8** (через сервис 6) |
| 0x36 | 0x080043EC | GET INFO: 0x42 байта данных приложения + поле ver |
| 0x37 | 0x08004416 | **LAUNCH**: сравнение 3 слов идентификации → state=2 → запуск приложения 0x08005000 |

Обработчик 0x37:

```asm
0x08004416: ldrh  r0, [r4, #1]     ; длина == 0x0C (3 слова)
0x0800441C: bne   err              ; иначе ошибка
0x08004426: ldr   r0, [r5]         ; state (0x20001400) == 0
0x08004428: cbnz  r0, 0x0800446E   ; state != 0 -> статус 7
            ; get_identification(0x08004604): 3 слова из EEPROM-слотов
0x08004442: ldr   r0, [sp, #8]     ; word_ver  vs запрос+4
0x0800444A: ldr   r0, [sp, #4]     ; word_crc  vs запрос+8
0x08004452: ldr   r0, [sp, #0xC]   ; word_size vs запрос+0xC
            ; любое несовпадение:
0x0800446E: movs  r0, #7           ; <<<< СТАТУС 7
0x0800445A: movs  r0, #2 ; str [r5]  ; при совпадении: state=2 -> запуск приложения
```

### Функция идентификации stub'а (0x08004604)

Читает «виртуальные регистры» EEPROM через сервисы бутлоадера (опкод 5 =
«чтение EEPROM-слота», таблица сервисов [0x0800017C]):

```
slot N -> адрес 0x08002800 + (N + 0x40)*2      (активная страница EEPROM
                                                выбирается маркером 0x5AA5
                                                в конце страницы, 0x08002FFE)

word_ver  = slot6 << 16 | slot5    (адреса 0x0800288C, 0x0800288A)
word_crc  = slot8 << 16 | slot7    (адреса 0x08002890, 0x0800288E)
word_size = slot4 << 16 | slot3    (адреса 0x08002888, 0x08002886)
```

Слоты 3–8 записываются **только** обработчиком 0x35 в процессе штатного
обновления. В донорском дампе 2.21.32 (а значит и в собранном из него образе
2.22.3) эти адреса — **0xFF** → идентификация = {0xFFFFFFFF, 0xFFFFFFFF,
0xFFFFFFFF}.

## Что присылает ПК в команде 0x37

Реверс `sm2lib.dll` 2.22.3 (525 432 байта, не обфусцирована):

* **FUN_1000C760** — заполнение записей обновления (имmediates в коде):
  stub: seed 0x7821AB35, ver 0x1198, size 0xB00, crc 0x2912D0A0;
  app:  ver 0x1198, size 0x1353C, crc 0x210E9A13 (официальные параметры).
* **FUN_1000CD50** — общий сценарий подключения:
  1. **FUN_1000BB30**: команда **0x83** (INFO бутлоадера) → разбор ответа:
     serial (body+0, значение 0x0A111788 = «A111788»), ver (body+0xC — из
     загрузочной записи EEPROM @0x08002804), тип (body+0x10).
  2. Если прошитая версия ≠ 0x1198 → сценарий обновления:
     **FUN_1000C940** (этап 1: команды 0x80/0x81/0x82 бутлоадера + 0x8B) →
     команда **0x88** (ARM: state=2, бутлоадер запускает то, что лежит по
     0x08004000, т.е. наш stub) → **FUN_1000CB70** (этап 2: команды
     0x33/0x34/0x35 stub'а — запись приложения и EEPROM-слотов, затем 0x36).
  3. Команда **0x37** (LAUNCH) с телом **{ver=0x1198, crc=0x210E9A13,
     size=0x1353C}** — берутся из записей sm2lib.dll, НЕ из ответов устройства.
  4. Если ответ на 0x37 ≠ 0 — ошибка с этим кодом: **статус 7 → [0007]**.
     (Дополнительно: `cmovne edi, 7` при несовпадении ver в ответе 0x36 —
      тот же текст ошибки.)

### Важное открытие: список серийных номеров «не обновлять»

Обе функции обновления (FUN_1000C940 и FUN_1000CB70) начинаются с проверки
серийного номера устройства (FUN_1000C830: 27 констант, обфусцированы
XOR 0x33335555; первая из них после деобфускации — **0x0A111788 = A111788,
серийник донора!**). Для серийников из списка **обновление пропускается
целиком** (мгновенный `return 0`). Судя по всему, это внутренние/тестовые
приборы Scanmatik — клон сняли именно с такого прибора.

Следствие: ПК-программа для нашего устройства **никогда не выполнит** этап 2
(запись приложения и EEPROM-слотов 0x35) — значит, корректную
«книжную» информацию в EEPROM обязан содержать сам образ прошивки.

## Корневая причина

В собранном образе EEPROM-слоты 3–8 (0x08002886–0x08002891) пусты (0xFF от
донора). Stub при команде 0x37 сравнивает их с ожидаемыми ПК значениями
{ver=0x1198, crc=0x210E9A13, size=0x1353C}, получает 0xFFFFFFFF…, отвечает
статусом 7 → ПК показывает **[0007]**. Приложение никогда не запускается.

Дополнительный (косметический) дефект: загрузочная запись EEPROM
{crc=0xBDEE4E94, ver=0x1070, size=0xB2E0} осталась от 2.21.32, поэтому
бутлоадер в ответе 0x83 сообщает версию 0x1070, и ПК каждый раз пытается
уйти в сценарий обновления (для нашего серийника он безвредно
пропускается, но медленнее и не соответствует «настоящему» прибору 2.22.3).

Примечание: «проверка CRC при старте» бутлоадера (FUN_080011A8) читает
загрузочную запись, но **в обеих ветвях возвращает 1** («валидно») —
функционально отключена, поэтому несовпадение crc в загрузочной записи
ни на что не влияет.

## Исправление

В полный образ добавлены:

1. **EEPROM-слоты 3–8** (идентификация запуска, сравнивается командой 0x37):

| Слот | Адрес | Значение | Слово |
|------|-------|----------|-------|
| 3 | 0x08002886 | 0x353C | size = 0x0001353C (мл.) |
| 4 | 0x08002888 | 0x0001 | size (ст.) |
| 5 | 0x0800288A | 0x1198 | ver = 0x00001198 (мл.) |
| 6 | 0x0800288C | 0x0000 | ver (ст.) |
| 7 | 0x0800288E | 0x9A13 | crc = 0x210E9A13 (мл.) |
| 8 | 0x08002890 | 0x210E | crc (ст.) |

   **Важно**: в слоты записан ОФИЦИАЛЬНЫЙ crc (0x210E9A13), а не crc
   патченного приложения (0xBB7A85CE) — stub при запуске **не пересчитывает**
   CRC приложения (только сравнивает слова с присланными ПК), а ПК присылает
   официальные значения из своих записей.

2. **Загрузочная запись** @0x08002800: {crc=0x210E9A13, ver=0x1198,
   size=0x1353C} — теперь команда 0x83 сообщает «2.22.3», ПК сразу видит
   актуальную прошивку.

Больше в образе не изменилось ни байта (проверено побайтовым сравнением:
21 байт в v2-full, 12 байт в v2-slots-only). Бутлоадер, серийник A111788,
крипто-блоб, маркер EEPROM-страницы 0x5AA5, виртуальный UID (0x080028E8),
stub и патченное приложение — без изменений.

## Прошивка (SWD)

Как и раньше, полный образ по адресу 0x08000000:

```
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
        -c "init; reset halt; flash write_image erase SM2Pro_full_flash_2.22.3_patched_v2.bin 0x08000000; reset run; exit"
# или
st-flash --format binary write SM2Pro_full_flash_2.22.3_patched_v2.bin 0x08000000
```

После перепитания подключить ПК-программу Scanmatik 2.22.3. Ожидаемая
последовательность: 0x83 (ver 2.22.3) → 0x88 (запуск stub'а) → 0x37
(идентификация совпадает) → приложение запускается → обычная работа J2534.

## Почему это не «кирпич» и что если не поможет

* Ошибка [0007] — программная (несовпадение слов идентификации), устройство
  полностью управляемо: бутлоадер и stub отвечают на команды, прошивку можно
  менять сколько угодно.
* Если вдруг ПК-программа предложит «обновить прошивку» — для серийника
  A111788 обновление будет молечно пропущено (список), патч не сотрётся.
  Для других серийников штатное обновление перезапишет приложение
  официальным (патч UID пропадёт, устройство останется рабочим).
* CRC-проверка целостности при запуске в бутлоадере отключена (всегда
  «валидно»), поэтому патченное приложение (crc 0xBB7A85CE при официальной
  записи 0x210E9A13 в EEPROM) стартует без ограничений.

*Анализ: capstone (Thumb-2) по дампам бутлоадера/stub и x86 по sm2ptconfig.exe
и sm2lib.dll 2.22.3; скрипты `fw_analysis/build_v2_fix.py` (сборка),
`fw_analysis/new_dist/disasm_stub.py` (дизассемблер stub'а).*
