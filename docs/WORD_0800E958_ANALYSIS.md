# Анализ отличающегося слова 0x0800E958 (донор vs официальная прошивка 2.21.32)

## Резюме

Единственное отличие донорского дампа от официального образца приложения —
**одно 32-битное слово по адресу флеша 0x0800E958** (смещение в файле 0x0E958,
смещение 0xA958 от база приложения 0x08004000):

| Образ | Значение | Смысл |
|-------|----------|-------|
| Официальный (из sm2lib.dll) | `0x1FFFF7E8` | Адрес **96-битного Unique Device ID** STM32F105 в системной памяти (заводская электронная сигнатура: X/Y координаты кристалла на пластине — слово 0, номер пластины — слово 1, ASCII-номер лота — слова 2-3, всего 12 байт 0x1FFFF7E8..0x1FFFF7F3) |
| Донор (клон) | `0x080028E8` | Адрес в **EEPROM стр.1** (0x08002800..0x08002FFF), куда производитель клона записал «виртуальный UID»: слово `0x3247F69E` (0x080028E8) и байт `0x43` (0x080028F3) — записаны ровно те байты, которые читает код, остальное 0xFF |

**Важно: прежний вывод о «мёртвой, ни разу не используемой ячейке» НЕВЕРЕН.**
Слово активно используется кодом приложения.

## Где находится и кто его читает

- Слово — ячейка **пула литералов** функции `0x0800E764` (пул 0x0800E94C..0x0800E964:
  `0x9723D988, 0x3EA816AB, 0xF97FAAE1, [НАШЕ СЛОВО], 0x47139847, 0xF8124939, 0xE97DEE16`).
- Загружается ровно одной инструкцией: `0x0800E7CC: ldr r0, [pc, #0x188]`.
- Функция `0x0800E764` — **обработчик команды 0x12** внутреннего протокола ПК↔адаптер
  (таблица команд: база 0x0800F174, 42 записи {код:1б, флаги:1б, пад:2б, обработчик:4б},
  диспетчер — функция 0x0800BC44: сканирует таблицу по байту-коду из принятого сообщения,
  при совпадении вызывает обработчик; у команды 0x12 флаги = 0 → доступна всегда).
- Вторая функция пула `0x0800E814` — обработчик **команды 0x16** (второй раунд того же протокола).

## Как используется (ревер функции 0x0800E764, команда 0x12)

```asm
0x0800E7CC: ldr   r0, [pc, #0x188]   ; r0 = 0x1FFFF7E8 (UID) / 0x080028E8 (EEPROM клона)
...
0x0800E7D4: ldrb  r2, [r0]           ; байт 0 UID (мл. байт координат X/Y)
0x0800E7D6: ldr   r1, [r0]           ; слово 0 UID (координаты X/Y на пластине)
0x0800E7D8: ldrb  r0, [r0, #0xB]     ; байт 11 UID (символ номера лота)
0x0800E7DA: add.w r1, r1, r2, lsl #12
0x0800E7DE: add.w r0, r1, r0, lsl #10
0x0800E7E2: str   r0, [r5, #0x14]    ; «отпечаток UID» -> поле +0x18 ответа
```

Функция целиком — **challenge/response аутентификация адаптера**:

1. Из запроса ПК берутся два 32-битных значения (челлендж, смещения +5 и +9 в пакете).
2. Смешиваются с внутренними счётчиками устройства (сервисные опкоды 7 и 8 через
   диспетчер 0x08004408 — обёртки 0x0800BAA8/0x0800BAC8).
3. Прибавляется 64-битная константа `0x3EA816AB9723D988`, хеш через опкод 9 (0x0800BADC),
   умножение на 0x21 (umull), повторный хеш.
4. В ответ ПК (тег 0x60) укладываются 6 слов: [счётчик, хеш_1, хеш_2, x, y, **отпечаток UID**].

Родственная функция 0x0800E814 (команда 0x16, ответ с тегом 0x10) — второй раунд:
константы 0x47139847/0xF8124939/0xE97DEE16, умножение на 0x39, XOR 0x83838383,
поля запроса [r0+5]/[r0+9] те же.

## Подтверждение на стороне ПК

В драйвере `smj2534.dll` (file:0x30BB45) и основной программе `smwin.exe` (file:0x2C2710)
найдена та же константа в 64-битной арифметике: `adc ecx, 0x3EA816AB` / `adc edx, 0x3EA816AB`
(обфусцированный код в скрытой секции — у обоих файлов нестандартно раздутый .reloc ~3-4 МБ).
Т.е. ПК воспроизводит ту же математику и **проверяет ответы устройства** — это
защита «прибор ↔ ПО» с общим секретом.

## Что даёт патч клона

Клон читает «UID» из EEPROM и всегда сообщает ПК константный отпечаток:

```
uid_fp(клон) = 0x3247F69E + 0x9E*0x1000 + 0x43*0x400 = 0x3252E29E
```

Все устройства этой партии клонов сообщают ПК **один и тот же «идентификатор»**
(видимо, скопированный с одного оригинального прибора, с которого снимали прошивку).
Возможные причины патча:
- привязка ПО/лицензии к идентификатору прибора (все клоны = «одно устройство»);
- на платах клонов стоят перемаркированные кристаллы, где чтение настоящего UID
  по 0x1FFFF7E8 ненадёжно/даёт мусор — патч даёт контролируемое значение.

## Практические выводы для восстановления

| Прошивать | Поведение | Риск |
|-----------|-----------|------|
| `restored.bin` (слово 0x1FFFF7E8) | Устройство сообщает ПК отпечаток UID **своего** чипа — уникальный, как у настоящего Scanmatik-2 | Если чип — настоящий ST/совместимый, работает как оригинал. Если перемаркированный китаец без UID по этому адресу — будет читаться мусор (вероятно не критично, но не гарантированно) |
| `donor_asis.bin` (слово 0x080028E8) | Устройство сообщает константный отпечаток 0x3252E29E — **в точности как рабочий донорский клон** | Минимальный: поведение идентично работавшему прибору; все донорские настройки EEPROM сохранены |

Оба файла содержат и EEPROM-данные с «виртуальным UID» (0x080028E8 = 0x3247F69E),
и отличаются ВСЕГО этим одним словом друг от друга во всём 256КБ образе.

Рекомендация: если чип на плате — гарантированно ST, можно лить `restored.bin`;
если есть сомнения (noname-плата, перемаркировка) — надёжнее `donor_asis.bin`
(полная идентичность поведения рабочему донору).

Примечание: при штатном обновлении прошивки через ПО Scanmatik зальётся официальный
образ — патч клона сотрётся и устройство перейдёт на чтение настоящего UID.
Это нормально и штатно.

скрипты check_word.py / check_word2.py / check_func.py / trace_usage.py /
find_dispatcher.py в каталоге fw_analysis.*
