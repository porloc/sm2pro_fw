# ПРОМПТ ДЛЯ CLAUDE CODE + J-LINK MCP (локальная живая отладка SM2 Pro)

Скопируй текст ниже в Claude Code на ПК, где J-Link подключён к адаптеру SM2 Pro.
Задача — только собрать данные (прошить готовый образ, поставить точки останова,
снять дампы). Никакого анализа — анализ делается отдельно.

---

Помоги снять диагностику с платы через J-Link.

Плата: автомобильный диагностический адаптер, мой собственный.
МК — Cortex-M3, STM32-совместимый (256 КБ flash, 64 КБ RAM).
Нужно посмотреть, какие пакеты шлёт ПК-программа устройству после запуска
его приложения: у устройства есть обработчик служебной команды 0x103,
и нужно снять дампы его входного буфера.

Правила:
- Используй MCP-инструменты J-Link (connect / halt / resume / read_registers /
  read_memory / write_memory / set_breakpoint / clear_breakpoint / savebin /
  loadfile и т.п., по факту доступные).
- Точки останова — только аппаратные (SetBP). Ничего не стирать и не менять
  во flash, кроме шага 1 (заливка готового образа целиком).
- Все результаты складывай в папку ./debug-out/, каждое действие и ответ
  J-Link дублируй в debug-out/session.log.
- Ошибка на шаге — не блокер: запиши её в session.log и иди дальше.
- Все savebin делай при останованном ядре.

Шаги:

1. Заливка образа. Файл `firmware/SM2Pro_full_flash_2.22.3_AUTH_TABLE+PID2_v2.bin`
   из репозитория https://github.com/porloc/sm2pro_fw (скачай заранее в текущую
   папку). Залей по адресу 0x08000000 (loadfile), затем reset и run.
   Подключение: SWD, 2000 кГц, устройство STM32F105VC
   (если не подойдёт — GD32F305RC, затем generic Cortex-M3).

2. Бэкап области настроек (перед экспериментом):
   savebin debug-out/eeprom_backup.bin, 0x08002800, 0x1000

3. Точки останова (пока ядро остановлено):
   SetBP 0x08007E60    (вход обработчика команды 0x103)
   SetBP 0x08007F50    (конец ветки записи таблицы)
   Затем отпусти ядро (g / resume).

4. Пользователь запускает ПК-программу Scanmatik 2.22.3 и пробует подключиться
   к адаптеру. Жди останова на точке. Если останов случился:
   a) выведи все регистры (regs) — особенно PC, LR, R0;
   b) R0 — это указатель на пакет: сними 0x120 байт начиная с адреса в R0
      (savebin debug-out/cmd_packet_N.bin, <значение_R0>, 0x120);
   c) полный снимок RAM: savebin debug-out/ram_N.bin, 0x20000000, 0x10000;
   d) зафиксируй, что в этот момент показывает ПК-программа (текст/код ошибки);
   e) отпусти ядро (g).
   Нумеруй файлы N=1,2,3... на КАЖДОЙ новой остановке на любой из точек.
   Ожидается от 1 до 4 остановок.

5. Если за 60 секунд после появления ошибки в ПК-программе остановок не было:
   останови ядро (h), выведи regs, сними savebin debug-out/ram_idle.bin,
   0x20000000, 0x10000 и отпусти ядро.

6. Итог: список файлов в debug-out с размерами + краткое резюме:
   сколько было остановок, на каких адресах (PC), значения R0 на каждой,
   что показывала ПК-программа.

Не продолжай (`g`) с мягкой точкой останова в flash: если при проверке
`mem16 0x08007292, 1` видишь 0xBE00 — сообщи, это признак остатка старой
soft-BP (ожидалось 0xB118).
ClrBP принимает HANDLE из SetBP (1, 2, 3...), не адрес.

## Результаты
Папку debug-out целиком нужно передать для анализа (загрузить в репозиторий
porloc/sm2pro_fw в папку dumps/ или переслать пользователю для загрузки).

## Памятка (НЕ для локального Claude — контекст для нас)

* Образ v2 = SWDON-база (SWD живёт после LAUNCH — без этого точки невозможны)
  + таблица regs 0x39..0xB8 из рабочего дампа 2.21.35 (A71283)
  + слоты LAUNCH {size=0x1353C, ver=0x1198, crc=0x210E9A13} @0x2886
    (обязательно: пустые/чужие слоты → стаб вернёт 7 → экранная [0007],
    приложение не запустится — проверено по дизассемблеру 0x08004416/0x08004604)
  + PID 0x0002 в idProduct @0x0800271C (дескриптор @0x08002712, литерал
    0x080019D0; конфиг-дескриптор @0x08002724 — НЕ трогать, старый патч туда
    писал и ломал перечисление USB).
* Смысл прогона: с PID 0x0002 драйвер даёт имя \\.\SmUsb_PID_0002_000 →
  ПК-программа идёт по новой ветке протокола и (по гипотезе) шлёт 0x103
  (чтение таблицы mode 0x00 / запись+сверка mode 0x99). Дамп R0 на входе
  0x08007E60 даст точное содержимое пакета: режим, слово reg0x38 и 128
  полуслов таблицы. Остановка на 0x08007F50 = ветка записи (смотрим,
  что именно ПО пишет и что возвращает статус).
* Ожидания по экрану: пока CPU стоит на точке, ПО через ~1.4 с покажет
  таймаут/ошибку — это нормально, данные уже сняты.
* Если остановок нет вообще — ПК не дошёл до 0x103 (другая команда раньше
  или ветка не включилась) → ram_idle.bin покажет состояние; дальше
  ставим точку на диспетчер сообщений приложения.
