# Захват API Monitor: ПОЛНЫЙ обмен smwin ↔ адаптер расшифрован

Дата: захват прислан 19.11 (файл capture.apmx86, 2,17 МБ, 97 вызовов).
Мониторился `C:\Program Files (x86)\Scanmatik\smwin.exe` (32-бит) с загруженными
Sm2Lib.dll, PlxLib.dll, Obd2.dll, IPHLPAPI.DLL.

Бинарный формат .apmx86 разобран полностью (ZIP: definitions + process/0/{info,calls,data}).
Ключ: поле @36 записи вызова = указатель на запись API в базе определений:
`0x57281A = CreateFileW`, `0x579BD2 = DeviceIoControl`, `0x579F1A = CloseHandle`.

## 2. Рабочий цикл (t = 138…9977 мс) — опрос статуса

82 DeviceIoControl в повторяющихся циклах по 9 вызовов, два чередующихся
буфера-контекста (0x015C7088, 0x015C8126). Размеры структур: 0x150 (336 Б),
0xBC (188 Б), 0x40 (64 Б), малые 7/13/18/22/40 Б. Внутри — статусные поля и
счётчики драйвера (растут: 0xB851, 0xB852…), хэндл 0x374 прошивает все структуры.

Интервал опроса адаптивный: 138 → 304 → 367 → … → 5212 → 2802 мс (backoff).

Обмена с автомобилем в записи НЕТ (только статус прибора) — J2534-сессия
не открывалась.

## 4. Ответ на вопрос «почему USBPcap не видел»

Обмен ЕСТЬ и идёт через \Device\SmUsb000 → smndis.sys → USB (VID 20A2:0001).
Значит, все прежние нулевые захваты USBPcap — это окно записи не туда/не тогда
или снятые галочки устройств в дереве фильтра USBPcap, а не отсутствие трафика.
Теперь, когда момент обмена известен точно (сразу после запуска действия в smwin),
USBPcap-трейс снимется без проблем: старт захвата → подключение в smwin → стоп.
