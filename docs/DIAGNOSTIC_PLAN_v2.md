# Диагностика «Внутренняя ошибка микропрограммы 00000» — план тестов v2

Дата: после отчёта «прошил все тест образы — везде та же ошибка 00000».

## Главный вывод этого этапа

Результат «все образы → 00000» **не означает, что железо сломано** и не
означает, что все образы одинаково нерабочие. Для части комбинаций эта ошибка
**гарантированно ожидаема** — из-за жёсткой привязки версий «прошивка ↔ ПО»
(доказательство ниже). Настоящая проблема ровно одна: **приложение 2.22.3,
запустившись, не отвечает ПК**. Два новых диагностических образа (PROBE и
MODE1) позволят точно определить, где именно всё ломается, — см. «План
тестов».

## Почему донорский образ 2.21.32 + НОВОЕ ПО 2.22.3 обязан дать «00000»

Механика (установлена реверсом sm2lib.dll 2.22.3, функции FUN_1000C830 /
FUN_1000C940 / FUN_1000CB70 / FUN_1000CD50):

1. smwin 2.22.3 при подключении читает версию прошивки (команда 0x83).
   У донора 2.21.32 это 0x1070, новое ПО ждёт 0x1198 → запускается сценарий
   обновления.
2. Обе ступени обновления начинаются с проверки серийного номера по списку
   «не обновлять» (27 констант, обфусцированы XOR 0x33335555). Серийник
   донора **A111788 в списке есть** (константа 0x392242DD = A111788 ^
   0x33335555, адрес 0x1000C8DC) → **обновление молча пропускается**.
3. Дальше ПО шлёт 0x88 ARM (бутлоадер запускает приложение 2.21.32 по
   0x08004000 — одноступенчатая архитектура) и затем команду 0x37 LAUNCH
   **протокола стаба 2.22.3** с параметрами {0x1198, 0x210E9A13, 0x1353C}.
   Приложение 2.21.32 команды 0x37 не знает → ответа нет → тайм-аут →
   smwin показывает «Внутренняя ошибка микропрограммы 00000».

То есть донорский образ, проверяемый новой программой, **заведомо** даст
«00000». Этот тест ничего не говорит о железе. Единственная осмысленная
проверка донорского образа — со **СТАРЫМ ПО 2.21.32** (см. план тестов).

## Что выяснено о причине «00000» у образов 2.22.3 (глубокий реверс)

Проверены и **отвергнуты** следующие гипотезы:

| Гипотеза | Проверка | Итог |
|----------|----------|------|
| Патч UID (9 слов) ломает приложение | Тест B (official_v2, без патча) — та же ошибка | НЕ ОНА |
| Приложение переконфигурирует тактирование и срывает USB-часы | В приложении 2.22.3 нет ни одной записи RCC_CR/RCC_CFGR (только APB2ENR/APB1RSTR — включения тактирования и сброс TIM2-7/CAN1/CAN2) | НЕ ОНА |
| Шторм USB-прерываний после смены VTOR (USB SIE делит IRQ19/20 с CAN1) | USB у прибора — **OTG_FS (0x50000000)**, а не SIE; стек полностью в бутлоадере и **поллинговый**: векторы IRQ19/20 бутлоадера — заглушки «b .», прерывания USB не используются вовсе | НЕ ОНА |
| Приложение поднимает свой USB-стек и конфликтует с бутлоадером | В приложении 2.22.3 **ноль** обращений к USB-периферии (ни 0x5000xxxx, ни 0x40005Cxx): связь идёт **только через сервисы бутлоадера** 0 (приём пакета) / 1 (отправка) / 3 (тик) / 13 (регистрация), ровно как у стаба | НЕ ОНА |
| Колбэк, регистрируемый приложением через сервис 13, не вызывается старым бутлоадером | Колбэк 0x08017875 — **пустышка** «nop; bx lr»; донорский бутлоадер его и не вызывает (поле только записывается). Регистрация безвредна | НЕ ОНА |
| Конфликт RAM (данные бутлоадера против .bss приложения) | Линкер-скрипт приложения резервирует область бутлоадера: данные приложения начинаются с 0x20001418, стек бутлоадера 0x20001418–0x20001800 не пересекается | НЕ ОНА |

Установленная архитектура связи 2.22.3 (важно для понимания):

```
USB-хост ←→ OTG_FS (0x50000000, ПОЛИНГ, без прерываний)
            └── стек USB целиком в БУТЛОАДЕРЕ (донор 2.21.32)
                └── машина состояний 0x200000C4, буфер пакета 0x200000F5E
                    └── сервисы: 0=принять пакет (сам обрабатывает команды
                        бутлоадера 0x80–0x8A, остальное отдаёт вызывающему),
                        1=отправить ответ, 3=тик, 13=таймауты+колбэк
                        └── их использует и СТАБ 2.22.3 (РАБОТАЕТ:
                            0x33–0x37 отвечаются!) и ПРИЛОЖЕНИЕ 2.22.3
```

Стаб на том же бутлоадере и тех же сервисах работает — значит сам транспорт
совместим. Не отвечает именно **приложение**. Оставшиеся кандидаты (статически
неразличимы, код приложения обфусцирован control-flow flattening):

1. приложение падает/зависает в одной из 240 init-записей протокольной
   таблицы или в обфусцированном обработчике первой команды;
2. приложение зависит от **изменённой семантики сервисов бутлоадера нового
   поколения** (бутлоадер 2.22.3 в дистрибутиве ПК-ПО отсутствует — там
   только стаб+приложение, взять неоткуда);
3. приложению нужны **данные, записываемые командой 0x8B** (0x68 байт на
   запись приложения: доп1 0x20 @0x10045F98 + доп2 0x48 @0x10045F50 в
   sm2lib.dll — извлечены; отправляются ТОЛЬКО если бутлоадер ответил на
   0x82 кодом 0x18 или 1, т.е. только новому поколению; куда их пишет новый
   бутлоадер — неизвестно, самого бутлоадера нет).

## Новые диагностические образы

Оба собраны на базе `SM2Pro_full_flash_2.22.3_patched_v2.bin` (EEPROM-слоты
и загрузочная запись исправлены — [0007] не вернётся). Изменения минимальны
и проверены дизассемблированием.

### 1) `SM2Pro_full_flash_2.22.3_PROBE_stub_resident.bin` — ГЛАВНЫЙ ТЕСТ

Единственное отличие: в стабе 2.22.3 команда 0x37 LAUNCH больше не
переводит state=2 (запись `str r0,[r5]` @0x080045C заменена на NOP).
Приложение **не запускается вообще**; стаб остаётся жить в своём цикле и
штатно отвечает:

* 0x33–0x37 — как обычно (0x37 честно вернёт {status=0} — ПК сочтёт запуск
  успешным!);
* любую другую команду — статусом 1 (штатный путь неизвестной команды,
  0x080042F8 → ответ отправляется сервисом 1).

```
MD5:    555c9d9cd2568626ad6bb204da4b1d52
SHA256: ed04663074be6ef60ea83759cc8b15ce6925e1713fffde9070289a3e242582cf
```

**Интерпретация результата (smwin 2.22.3):**

* Появилась **любая ошибка, кроме «00000»** (скорее всего «[0001] Неверный
  параметр» на первой же пост-запускной команде) → транспорт после LAUNCH
  работает, стаб отвечает. Значит, на 100% виновато **приложение 2.22.3**
  (краш/зависание/несовместимость со старым бутлоадером или данными 0x8B).
  Дальнейший путь — п.3 плана тестов и решение «жить на 2.21.32».
* Снова **«00000»»** → после LAUNCH обмен не доходит даже до стаба —
  проблема в связке smwin/sm2lib (например, ПК переоткрывает устройство
  после «запуска» и теряет его). Это меняет направление расследования —
  сообщите результат.

### 2) `SM2Pro_full_flash_2.22.3_MODE1.bin` — проверка поколения платы

Единственное отличие: сервис 10 бутлоадера («режим платы») возвращает **1**
вместо 2 (`movs r1,#2` → `movs r1,#1` @0x080012CE). Приложение 2.22.3 при
режиме 1 берёт другую таблицу пинов (0x08018338 вместо 0x080183C9) и другой
служебный контур (TIM1 вместо ADC-схемы). Донорский бутлоадер жёстко зашивал
«2» — если ваш клон на самом деле плата поколения 1, приложение
инициализировало чужую периферию.

```
MD5:    f38cf7ba4329a3d6a6a3749307e1ce80
SHA256: f33434705384827f21a12b7659d3c6f8ad4bc9a43140f09e029101d2da5b661e
```

**Интерпретация:** ошибка изменилась/пропала → ваш клон — плата режима 1
(тогда рабочее решение собираем на этом варианте). Та же «00000» → версия
платы та же, гипотеза снята.

## План тестов (по порядку)

| # | Образ (по 0x08000000) | ПО | Что ожидаем | Что это значит |
|---|----------------------|-----|-------------|----------------|
| 1 | `SM2Pro_full_flash_2.22.3_PROBE_stub_resident.bin` | **smwin 2.22.3** (новый дистрибутив) | ошибка ≠ 00000 (вероятно [0001]) | транспорт ОК → виновато приложение 2.22.3 |
| 2 | `SM2Pro_full_flash_2.21.32_donor_asis.bin` | **СТАРОЕ ПО 2.21.32** (папка `driver/Scanmatik` из архива материалов, либо дистрибутив `Scanmatik2.21.32.zip` — их sm2lib.dll 451 584 байта, ждёт версию 0x1070) | прибор подключается и РАБОТАЕТ | железо и связка бутлоадер↔2.21.32 исправны; A111788 в skip-списке старого ПО отсутствует, версия совпадает — обновление не потребуется |
| 3 | `SM2Pro_full_flash_2.22.3_MODE1.bin` | smwin 2.22.3 | изменение ошибки | см. выше |
| 4 | (по ситуации) `sm2ptconfig.exe` из пакета 2.22.3 | — | точный код [00XX] вместо расплывчатого 00000 | его таблица кодов 0–21 детальнее текста smwin |

**Важно про тест 2:** это единственная комбинация «прошивка+ПО»,
гарантированно рабочая на «родном» для неё железе (донорский дамп — образ
работавшего прибора). Если она тоже падает — значит, ваш клон отличается от
донора аппаратно (поколение платы/обвязка), и тогда тест 3 становится
главным. Если работает — прибор уже можно использовать со старым ПО, а
2.22.3 добиваться по результатам тестов 1 и 3.

## Прошивка (SWD), как раньше

```
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
        -c "init; reset halt; flash write_image erase <файл>.bin 0x08000000; reset run; exit"
# или
st-flash --format binary write <файл>.bin 0x08000000
```

После заливки — перепитание устройства.

## Технические детали (для протокола)

* Сервисы бутлоадера (донор): таблица из 14 функций @0x080002EC, диспетчер
  0x080002CD (opcode<14). 0=принять пакет (0x0800122A: сам обслуживает
  команды 0x80–0x8A бутлоадера, прочие отдаёт вызывающему; −1=пакета нет),
  1=отправить/триггер машины состояний (0x08001784: state 3→4, 8→9),
  3=тик (0x080011F6), 4=полный ребут в бутлоадер (MSP=0x20001800, VTOR=
  0x08000000, все IRQ off, 0x08000252), 5/6=чтение/запись EEPROM-слотов,
  7=серийник, 8=ключ по индексу (0x08000184+idx*4), 9=CRC32, 10=режим
  платы (жёстко 2), 13=регистрация таймаутов+колбэка (0x08001976/0x08001980:
  поля +0x10/+0x14/+0x18/+0x1C структуры 0x200000C4; донорский бутлоадер
  поле +0x1C читает только при записи — никогда не вызывает).
* Машина состояний связи: структура 0x200000C4; state @+0xE (2/7=пакет
  готов, 3/8=пакет отдан, 4/9=ответ готов), буфер пакета 0x200000F5E.
  Управляется поллингом из главного цикла (стаба/приложения) через
  сервисы 0/1/3 — прерывания не используются.
* USB-стек бутлоадера: OTG_FS 0x50000000, указатель хранится в [0x20000000];
  эндпоинты: IN 0x900+ep*0x20, OUT 0xB00+ep*0x20 (функция 0x080026C8).
* Стаб 2.22.3: Reset 0x08004151 (SP=0x20001830) → main 0x080044DD: svc13
  {таймауты 0x800000, колбэк 0}, цикл «svc3 → если state==2 → запуск
  приложения → svc0 → диспетчер 0x33–0x37 → svc1». Неизвестная команда →
  статус 1 (0x080042F8 → 0x08004476 `strb r0,[r4]` → отправка).
* Приложение 2.22.3: Reset 0x08005151 (SP=0x2000FF30) → main 0x0800B7F0:
  cpsid i → svc10 (режим) → выбор таблицы пинов (1→0x08018338,
  2/3→0x080183C9; для 3 дополнительно [0x4002103C]|=0x80 — вне карты
  регистров F105, no-op) → init (EXTI, NVIC-приоритеты по таблице
  0x0801845C, сброс/включение TIM2-7+CAN1/2+DMA) → cpsie i → SysTick
  (LOAD=0x89543F) → ADC/TIM1-контур (для режима≥2: IRQ18 ADC) → таблица
  240 протокольных записей (0x0801823C, у каждой свой init) → svc13
  {таймауты, колбэк 0x08017875=nop} → главный цикл svc0/svc1(/svc3).
  Таблица команд приложения: 0x1C/0x1D/0x1E, 0x50/0x51/0x52, 0x01–0x0B,
  0x28, 0x0D, 0x53, 0x11–0x14, 0x17, 0x18, 0x19, 0x24, 0x26, 0x38, 0x1F,
  0x20, 0x21, 0x22 (auth 0x12 → 0x0800722C).
* Данные 0x8B (из sm2lib.dll 2.22.3, запись приложения):
  доп1 (0x20 байт) @VA 0x10045F98 (file 0x44998), доп2 (0x48) @VA 0x10045F50
  (file 0x44950); для записи стаба: 0x10059FF8 и 0x1005A018. Отправляются
  только при ответе 0x82 == 0x18 или 1 (новое поколение бутлоадера).
* Патчи образа PROBE: 0x445C: `28 60` (str r0,[r5]) → `00 BF` (nop).
* Патч образа MODE1: 0x12CE: `02 21` (movs r1,#2) → `01 21` (movs r1,#1).

*Анализ: capstone (Thumb-2/x86); скрипты `new_dist/dis_deep.py`,
`new_dist/dis_app2.py`, `new_dist/build_v4_probe.py`.*
