# Лог №2 + скриншот Диспетчера устройств: найдена вероятная ПРИЧИНА всех «00000»

## Входные данные

1. **Скриншот** Диспетчера устройств: адаптер виден как сетевой адаптер
   **«Scanmatik USB-NDIS #3»**, состояние «Устройство работает нормально»,
   изготовитель SCANMATIK EUROPE SL, размещение Port_#0002.Hub_#0001.
   Жёлтых знаков нет — драйвер установлен и запущен.
2. **Захват №2** (тот же файл на Drive, содержание заменено): 28,5 с, 13382 пакета,
   3 шины USBPcap.

## Что показал захват №2

- Адаптер присутствовал на шине **bus=1 dev=1** (bootloader-дескрипторы
  VID 20A2:0001, класс 0xFF, 2×bulk 64 Б) с начала записи.
- **С адаптером не обменялись ни одним байтом** — после перечисления в t=0
  ни одного пакета (ни bulk, ни control).
- В t≈6,6–7,2 с: адаптер **отключили** от порта (освободился адрес 1), и в
  t=7,19 с в порт воткнули **клавиатуру** (Holtek 04D9:1702 — она перечислилась
  и получила освободившийся адрес 1; похоже, перепутали кабель).
- До конца записи (ещё 21 с) адаптер **не возвращался** на шину.
  Bulk-трафика в записи нет вообще, ни с одним устройством.
- Ошибок со стороны адаптера нет: ни disconnect'а, ни stall, ни таймаута —
  его просто выдернули.

Вывод: и этот захват не содержит ни одной попытки обмена программы с прибором.
Два захвата — 51,5 с и 28,5 с — дают ноль пакетов адаптеру при работающем
(по Диспетчеру устройств) драйвере.

## РЕВЕРС-ИНЖИНИРИНГ: как ПК-софт находит прибор (новое, решающее)

Разобраны sm2lib.dll (525 КБ, не запакован), sm2ptconfig.exe, smj2534.dll,
smndis.sys (x86/x64) из дистрибутива 2.22.3.

### Цепочка обнаружения устройства

1. **Драйвер smndis.sys** создаёт сетевой адаптер и символьные ссылки
   `\Device\SmUsbNNN` / `\DosDevices\SmUsbNNN`, где **NNN — 3 hex-цифры номера
   экземпляра**. Первый экземпляр — `000`; при коллизии имени
   (STATUS_OBJECT_NAME_COLLISION / 0x40000000) номер увеличивается —
   в драйвере есть цикл повтора (smndis x64: `0x140001333` → форматирование
   имени → проверка `cmp eax,0xC0000035` → повтор с NNN+1).

2. **sm2lib.dll находит прибор ТОЛЬКО по имени сетевого подключения.**
   Функция перечисления (sm2lib `0x10002E20`):
   - получает таблицу интерфейсов (импорт `GetIfTable` из IPHLPAPI);
   - для каждого интерфейса сравнивает **первые 18 символов имени** с
     шаблоном **`DIRECT-SCANMATIK-#`** (строка sm2lib @0x10069930);
   - находит в имени `#`, затем `swscanf(после_#, "%X", &num)` — парсит
     **hex-число** после решётки;
   - результат передаётся дальше как «найдено устройство № num».

3. **Открытие устройства** (sm2lib `0x10009000`): строит имя
   `\\.\SmUsbNNN` (шаблон `\\.\SmUsb000` @0x1006A128, последние 3 цифры
   перезаписываются hex-цифрами счётчика) и в цикле
   **пробует NNN = 000…009** (`cmp edi,0xA`):
   `CreateFileW(name, 0, 0, NULL, OPEN_EXISTING, 0, NULL)`;
   первый успешно открывшийся — используется; при ошибке проверяется
   GetLastError()==5 (ACCESS_DENIED). Максимум **10 попыток**.

4. **Имя подключения `DIRECT-SCANMATIK-#XXXXX` никем не создаётся само:**
   - smndis.inf НЕ прописывает имя соединения (только Ndi-параметры);
   - DrvInstX64.exe (установщик драйвера) не содержит логики переименования;
   - имя ставит **только прикладной софт вендора** — в sm2ptconfig.exe,
     sm2DPDUApi_x64/x86.dll и smj2534.dll есть формат
     **`DIRECT-SCANMATIK-#%05X`** (5 hex-цифр; sm2ptconfig @0x482908,
     вызов wsprintf в `0x434B3C`). Число — из полей информации об адаптере
     (вероятно, производное серийного номера; для серийника 0x0A111788 —
     предположительно `#11788`).
   - **sm2lib.dll умеет только ИСКАТЬ по этому имени — переименовывать
     не умеет** (нет формата %05X, нет записывающих registry-API).
   - Все модули собраны с манифестом **`asInvoker`** — без прав администратора
     переименование сетевого подключения (запись в
     HKLM\SYSTEM\CCS\Control\Network\...\Connection\Name) молча не сработает.

### Следствие: перенос порта/переустановка ломает видимость прибора

При смене USB-порта (или переустановке драйвера) Windows создаёт **новый
экземпляр устройства** с **новым подключением и именем по умолчанию**
(«Ethernet», «Сеть» и т.п.). Фирменное имя `DIRECT-SCANMATIK-#…` на новом
экземпляре **слетает**, и sm2lib больше не находит прибор: перечисление
возвращает пустой список → обмен не начинается вообще → ни одного пакета
на USB → таймаут → «00000».

У пользователя адаптер сейчас — **экземпляр №3** («Scanmatik USB-NDIS #3»),
и недавно переносился из хаба в прямой порт. Это идеально согласуется с
картиной захватов (ноль пакетов) и объясняет, почему **ВСЕ** тестовые образы
(v2, PROBE, MODE1 и даже донорский 2.21.32) дали одинаковые «00000» —
**дело не в прошивке, прибор просто невидим для программы**.

Ошибка **[0007]** на v1 была получена раньше — когда прибор ещё был виден:
это была настоящая ошибка обмена/прошивки. Затем (перенос порта/переустановка
между тестами v1 и v2) видимость сломалась — и все последующие «00000» уже
не связаны с содержимым прошивок.

## Что проверить (2 минуты)

1. **Win+R → `ncpa.cpl`** (Сетевые подключения) → найти подключение
   Scanmatik-адаптера → посмотреть его **имя**.
   - Ожидается при исправной настройке: `DIRECT-SCANMATIK-#xxxxx`
     (для этого адаптера предположительно `DIRECT-SCANMATIK-#11788`).
   - Если там «Ethernet N» / «Сеть N» / «Подключение по локальной сети N» —
     **это и есть корневая причина**.
2. В smwin — показывает ли список устройств прибор вообще.

## Лечение (если имя сброшено)

1. Адаптер подключён. Закрыть smwin.
2. Запустить **sm2ptconfig.exe от имени администратора** (ПКМ → «Запуск от
   имени администратора») — утилита конфигурации из комплекта; она должна
   найти адаптер и переименовать подключение в `DIRECT-SCANMATIK-#…`.
3. Запустить **smwin тоже от администратора** (для верности) и повторить
   прошивку.

## Если имя вдруг правильное — контрольный тест PowerShell

Запуск в обычном PowerShell (проверяет ровно то, что делает sm2lib —
открытие `\\.\SmUsb000`…`009`):

```powershell
Add-Type -TypeDefinition 'using System; using System.Runtime.InteropServices; public class K { [DllImport("kernel32.dll", CharSet=CharSet.Unicode, SetLastError=true)] public static extern IntPtr CreateFileW(string n, uint a, uint s, IntPtr sa, uint d, uint f, IntPtr t); [DllImport("kernel32.dll")] public static extern bool CloseHandle(IntPtr h); }'
0..9 | ForEach-Object { $n = "\\.\SmUsb" + $_.ToString("D3"); $h = [K]::CreateFileW($n, 0, 0, [IntPtr]::Zero, 3, 0, [IntPtr]::Zero); if ($h -eq [IntPtr](-1)) { "$n : НЕ ОТКРЫВАЕТСЯ (err $([Runtime.InteropServices.Marshal]::GetLastWin32Error()))" } else { "$n : ОТКРЫЛСЯ"; [void][K]::CloseHandle($h) } }
```

- Если все 10 «НЕ ОТКРЫВАЕТСЯ» — драйвер не создал имена (проверить версию
  драйвера на вкладке «Драйвер»: в дистрибутиве 2.22.3 — **1.00.00.24**,
  27.04.2026).
- Если какой-то открылся — цепочка до открытия живая, копать глубже.

## Замечания к технике записи логов

- Во время записи **не трогать кабели**: в захвате №2 адаптер выдернули
  (и воткнули клавиатуру — вероятно, перепутали кабель), поэтому попытка
  прошивки в кадр не попала.
- Правильный порядок: адаптер воткнут → старт захвата → 2 с → запуск
  программы → ошибка → 3 с → стоп.
