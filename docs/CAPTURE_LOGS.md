# Снятие логов обмена ПК-программы Scanmatik с адаптером SM2 Pro

Задача: записать реальный USB-обмен между ПК-программой (smwin.exe /
sm2ptconfig.exe) и адаптером, чтобы увидеть, **что именно прибор отвечает в
момент, когда программа показывает «Внутренняя ошибка микропрограммы 00000»**.

> **Урок первого лога (см. `LOG1_FINDINGS.md`):** запись, начатая при уже
> открытом окне ошибки, не содержит обмена — программа к этому моменту уже
> всё сделала (или не смогла открыть устройство). Порядок строго такой:
> **сначала старт записи → потом запуск программы → подключение → ошибка →
> стоп записи.** Окно ошибки при этом можно не закрывать до остановки записи.

## Почему нужен именно захват USB (а не COM-сниффер)

Установлено реверсом прошивки и ПК-ПО:

| Параметр | Значение |
|----------|----------|
| Класс USB | **vendor-specific (0xFF)**, НЕ COM-порт |
| VID / PID | **0x20A2 / 0x0001** (дескриптор бутлоадера @0x08002712) |
| Эндпоинты | 2 × bulk по 64 байта: **0x81 IN** (прибор→ПК), **0x02 OUT** (ПК→прибор) |
| Драйвер на ПК | smndis.sys (биндит VID_20A2&PID_0001), создаёт `\\.\SmUsb000` |
| Кто открывает | sm2lib.dll: `CreateFileW("\\.\SmUsb000")` + Read/Write/DeviceIoControl |
| Встроенный лог | отсутствует (в sm2lib.dll строк логирования нет) |

Поэтому программы-сниферы COM-портов **бесполезны** — COM-порта просто нет.
Нужен захват на уровне USB-шины: он видит все bulk-пакеты независимо от того,
какой драйвер стоит посередине.

Известные команды протокола, которые будут видны в логе:

* бутлоадер: `0x83` INFO (серийник/версия/тип), `0x88` ARM (запуск образа),
  `0x82` опрос поколения, `0x80–0x8B` — команды обновления;
* стаб 2.22.3: `0x33–0x36`, `0x37` LAUNCH {ver, crc, size};
* приложение: `0x12` AUTH, `0x27` CONFIG (EEPROM-слоты), `0x01–0x53` — рабочий
  протокол (таблица из 240 записей).

## Инструмент: Wireshark + USBPcap (бесплатно)

1. Скачайте Wireshark для Windows x64: <https://www.wireshark.org/download.html>.
2. При установке компонент **USBPcap** должен быть отмечен галочкой
   (в современных сборках он включён по умолчанию).
3. Если антивирус спросит про установку драйвера USBPcap — разрешите.
4. Если после установки в списке интерфейсов Wireshark нет «USBPcap1» —
   переустановите Wireshark и отметьте USBPcap вручную.

## Пошагово: как записать лог

1. Подключите адаптер к USB. Прочее USB-оборудование (флешки, хабы) по
   возможности отключите — меньше мусора в записи.
2. Запустите **Wireshark от имени администратора** (ПКМ по ярлыку →
   «Запуск от имени администратора»).
3. В списке интерфейсов найдите **«USBPcap1»** (могут быть USBPcap2 и т.д. —
   по одному на каждый корневой хаб). Если непонятно, какой ваш: выделите все
   USBPcap сразу (Ctrl+клик) и пишите всё.
4. Нажмите синюю кнопку «Плавник» (Start capture) — запись началась.
5. **Вытащите адаптер из USB, подождите 3 секунды, вставьте обратно.**
   Так в лог попадёт перечисление устройства: дескрипторы, серийный номер —
   сразу увидим, что за прошивка живёт в приборе.
6. Подождите 10–15 секунд (прибор грузится).
7. Запустите smwin.exe и выполните подключение к адаптеру.
8. Дождитесь ошибки «Внутренняя ошибка микропрограммы 00000»,
   **сделайте скриншот окна**.
9. Закройте окно ошибки и программу.
10. В Wireshark нажмите красный квадрат (Stop).
11. **File → Save As** → имя файла (см. таблицу ниже) → тип
    «Wireshark — pcapng» → Сохранить.
12. До нажатия Stop адаптер из USB **не вынимать**.

Запись занимает обычно 1–20 МБ — Google Drive переваривает без проблем.

## Какие записи нужны (каждая — отдельный .pcapng)

| # | Имя файла | Прошивка в приборе | Программа | Что даст |
|---|-----------|--------------------|-----------|----------|
| 1 | `01_00000_repro.pcapng` | текущая (v2-патч 2.22.3) | smwin 2.22.3 | Воспроизведение 00000: на какой команде обрыв, есть ли ответ стаба после LAUNCH |
| 2 | `02_probe_stub.pcapng` | `SM2Pro_full_flash_2.22.3_PROBE_stub_resident.bin` | smwin 2.22.3 | Приложение не запускается вовсе, отвечает стаб: если 00000 осталась, а стаб в логе отвечает — проблема на стороне ПК |
| 3 | `03_gold_22132.pcapng` | `SM2Pro_full_flash_2.21.32_donor_asis.bin` | **СТАРОЕ ПО 2.21.32** | «Золотой эталон» рабочего обмена — образец, с которым сравним неудачные логи |
| 4 | `04_ptconfig.pcapng` (опц.) | текущая | sm2ptconfig.exe 2.22.3 | Точный код [00XX] вместо расплывчатой 00000 |

Примечания:

* **Сценарий 3 — самый важный.** Старое ПО — папка `driver/Scanmatik` из
  архива материалов или дистрибутив `Scanmatik2.21.32.zip`. Это же тест 2 из
  `DIAGNOSTIC_PLAN_v2.md`: прибор должен подключиться и работать как до
  поломки. Если работает — заодно получим и эталон, и подтверждение, что
  железо исправно.
* Сценарий 2 имеет смысл, даже если PROBE-образ уже проверялся «на глаз» —
  в логе будет видно то, что не показывает окно ошибки.
* Если времени мало — минимум: сценарии **1 и 3**.

## Как передать логи

1. Положите .pcapng-файлы в ту же папку Google Drive, что и раньше
   (или любую ссылку на файлообменник).
2. К каждой записи желательно приложить: скриншот ошибки, какой образ прошивки
   залит, какая программа запускалась (2.21.32 или 2.22.3).

## Обработка: парсер готов

Скрипт `scripts/parse_usbpcap.py` (чистый Python 3, без зависимостей):

```
python3 parse_usbpcap.py 01_00000_repro.pcapng -o report.txt
```

Что выдаёт:

* перечисление USB — VID/PID/серийный номер устройства;
* все bulk-пакеты «хост→прибор / прибор→хост» с hex-дампом;
* аннотации известных команд (0x83 INFO, 0x88 ARM, 0x37 LAUNCH, 0x12 AUTH…);
* паузы больше 100 мс — прямое доказательство тайм-аута и его длительности;
* поиск маркеров: серийник 0x0A111788, версия 0x1198, CRC 0x210E9A13 и т.п.;
* гистограмму кодов команд и итоговую статистику.

Самопроверка парсера: `python3 make_test_pcap.py && python3 parse_usbpcap.py
test_capture.pcapng` (генерирует синтетический лог с командами 0x83/0x88/0x37).

## План Б (если USBPcap не заведётся)

1. **Device Monitoring Studio** (HHD Software, есть триал) — модуль
   «USB Monitoring», тот же уровень захвата, что и USBPcap.
2. **API Monitor** (rohitab.com) — перехват CreateFileW/ReadFile/WriteFile/
   DeviceIoControl у процесса smwin.exe: покажет буферы уже на уровне
   `\\.\SmUsb000` (сложнее в настройке, но данные «чище»).
3. Если ничего не ставится — минимум: прогнать sm2ptconfig.exe из пакета 2.22.3
   с каждым образом и снять скриншоты его точных кодов [00XX].

## Что лог ответит на главный вопрос

Развилки диагноза после разбора записей:

* **После 0x37 LAUNCH стаб отвечает** (в 02_probe видны пакеты прибор→ПК),
  а smwin всё равно показывает 00000 → проблема на стороне ПК: разбор ответа,
  переоткрытие `\\.\SmUsb000`, несовпадение ожиданий ПО. Меняем подход —
  чинить надо связку на ПК, а не прошивку.
* **После 0x37 тишина даже от стаба** → транспорт/запуск: смотрим USB reset,
  переподключение, куда делось устройство.
* **Эталон 2.21.32 не работает тоже** (сценарий 3 с старым ПО) → проблема
  глубже: железо клона отличается от донора (поколение платы) — тогда главный
  тест становится MODE1-образом.
