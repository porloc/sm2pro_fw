# J-Link OB (Blue Pill) для SM2 Pro: прошивка и решающий дамп зависания

Гайд для самодельного J-Link OB на STM32 Blue Pill (прошивка «J-Link OB for
STM32F103»). Покрывает всё, что нужно для прибора SM2 Pro (клон Scanmatik-2
PRO, контроллер **STM32F105VCT6**, LQFP100, 256 КБ flash, 64 КБ RAM):

1. подключение по SWD;
2. проверку связи и прошивку образов (включая откат на 2.21.35);
3. **решающий эксперимент** — остановку зависшего ядра и дамп PC/RAM,
   который покажет ТОЧНОЕ место зависания 2.22.3.

Это адаптация инструкции из `docs/APIMON3_LADDER_ANALYSIS.md` (там она
написана под ST-Link + openocd; результат у J-Link тот же).

---

## 1. Подключение (4 провода)

Целевой контроллер: **STM32F105VCT6**, корпус LQFP100 (шаг ножек 0,5 мм).

| Сигнал  | Нога прибора (MCU) | Куда на J-Link OB |
|---------|--------------------|-------------------|
| SWDIO   | **PA13** = нога 72 корпуса | пин SWDIO разъёма OB |
| SWCLK   | **PA14** = нога 76 корпуса | пин SWCLK разъёма OB |
| GND     | любой GND платы (корпус USB-разъёма, «минус» конденсаторов питания) | пин GND разъёма OB |
| VCC     | 3V3 платы (выход стабилизатора) | пин VCC/VTref разъёма OB |

Правила:

* **Питание раздельное**: Blue Pill OB — от своего micro-USB, прибор — от
  своего штатного USB. Пин VCC на OB используется только как ИЗМЕРЕНИЕ
  напряжения цели (VTref) — питать прибор от OB нельзя.
* **Общий GND обязателен** (он и обеспечивается проводом GND выше).
* Логика OB 3,3 В = логика STM32 — совместимо. Ничего 5-вольтового не
  подключать.
* Провода короткие, до 15 см (дюпонты нормальные). Плохой контакт на
  SWDIO/SWCLK — причина №1 ошибок соединения.
* NRST не нужен.

**На стороне OB**: используйте разъём/пины, указанные в гайде, по которому
вы делали (или покупали) OB. У готовых сборок обычно подписан разъём
VCC/SWDIO/SWCLK/GND. J-Link не подключится, если SWDIO/SWCLK перепутаны
местами — если связь не появляется, первым делом сверяйте именно эти два
провода.

**Где взять сигналы на плате прибора**:

* Посмотрите на плату: у многих клонов есть непропаянные площадки/контакты
  возле MCU (иногда подписаны SWD/DIO/CLK). Прозвоните их мультиметром от
  ножек 72/76 — если звонятся, паяйте на них.
* Если площадок нет — припаивайте тонкий провод (0,1–0,2 мм / 30 AWG)
  напрямую к ножкам 72 (PA13) и 76 (PA14): залудить провод, точечно
  коснуться ножки на 1 секунду. Паяльник с тонким жалом, температура
  ~300–320 °C, флюс. GND/3V3 — на более крупных элементах (см. таблицу).
* Для уверенности сверьтесь с даташитом STM32F105xx (Doc ID 15956) —
  LQFP100: PA13 = pin 72, PA14 = pin 76.
* Провода можно оставить припаянными постоянно: пока ПО J-Link не
  подключено, OB не мешает прибору работать (проверено практикой SWD;
  если заметите странности в работе прибора — подключайте OB-провода
  только на время дамп-прогонов).

## 2. Софт

1. Скачайте и установите **SEGGER J-Link Software and Documentation Pack**
   (Windows): segger.com → Downloads → J-Link Software and Documentation
   Pack. Нужны две утилиты из комплекта:
   * **J-Link Commander** — `C:\Program Files\SEGGER\JLink\JLink.exe`
     (консоль, основной инструмент);
   * **J-Flash Lite** — GUI-прошивальщик (по желанию).
2. Если ПО пишет «The connected probe appears to be a J-Link clone» и
   отказывается работать — поставьте более старую версию пакета (архив
   версий на той же странице загрузок; обычно берут V7.88b или ниже).
   Для наших операций (SWD + flash) подходит любая версия.
3. Параметры подключения к прибору, которые будет спрашивать J-Link:

   ```
   Device: STM32F105VC
   Interface: SWD
   Speed: 1000–4000 kHz
   ```

   (F105**VC**T6 = как раз наш случай: 256 КБ, LQFP100. Если связь
   неустойчива — снижайте скорость до 1000.)

## 3. Проверка связи

Подключите оба USB, запустите `JLink.exe` и ответьте на три вопроса
(Device/If/Speed — см. выше). Затем:

```
JLink> mem32 0x08000000, 4
```

Ожидаемый вывод (для образов с донорским бутлоадером — v2, AUTH_BYPASS,
PROBE, MODE1, fw_22135 — первые слова одинаковые):

```
0x08000000 = 20001800 0800032D 08000335 08000337
```

Это векторная таблица: SP=0x20001800, Reset=0x0800032D. Если увидели её —
связь есть, прибор отвечает. Если `ERROR: Can not connect to target` —
проверяйте провода SWDIO/SWCLK/GND и наличие 3V3 на пине VCC.

**Идентификация того, что сейчас на плате** (первые слова не различают
образы — различает полный хэш):

```
JLink> savebin cur.bin, 0x08000000, 0x40000
JLink> qc
```

и в Windows:

```
certutil -hashfile cur.bin MD5
```

сверить с таблицей хэшей в README (например `d0a3aadf125b8ff190ad62ced4650dcc`
= patched_v2, `71174367f0592fa7385047d9d57374f3` = fw_22135).

ВАЖНО: чтение флеша/SWD работает только пока прибор находится в **бутлоадере
в простое** (сразу после перетыка питания, smwin НЕ запускался) либо под
connect under reset. После запуска приложения (LAUNCH) бутлоадер отключает
SWD — см. раздел 3а.

## 3а. Почему у работающего прибора SWD мёртв (LAUNCH убивает отладку)

Найдено реверсом (`scripts/scan_debug_block2.py`): бутлоадер **отключает SWD
в момент запуска приложения**. Единственная во всей прошивке запись битов
SWJ_CFG — функция 0x08000E14, вызываемая ТОЛЬКО из блока запуска приложения
(`bl 0x08000E14` на 0x0800133C; вход в блок — `b.w 0x0800132A` из хвоста
обработчика команды 0x37 LAUNCH, 0x080002A0):

```
0x08000E14: ldr   r0, [pc, #0x330]     ; r0 = 0x40010000 (AFIO)
0x08000E16: ldr   r1, [r0, #4]         ; AFIO_MAPR
0x08000E18: bic   r1, r1, #0x07000000  ; SWJ_CFG
0x08000E1C: orr   r1, r1, #0x04000000  ; SWJ_CFG = 100: JTAG-DP и SW-DP ВЫКЛ
0x08000E20: str   r1, [r0, #4]
```

(Тот же код в 2.21.35, доноре 2.21.32 и всех v2-образах — байты @0xE14
идентичны. Приложение SWJ_CFG не трогает: его обращения к AFIO_MAPR —
только ремап TIM/USART движка пинов J2534.)

Следствия:

* в простое бутлоадера (сразу после перетыка питания, smwin не запущен)
  SWD жив (SWJ_CFG = 000 по умолчанию): halt, RAM, а если не активен RDP —
  и чтение/запись флеша;
* после LAUNCH (т.е. всегда, когда приложение работает или зависло после
  него) SWD мёртв: живое подключение даёт «Failed to initialize DAP»,
  любые команды — «Could not read memory» / «CPU is not halted». Именно
  так было в логах прогонов A/B (живое подключение там не проходило
  никогда, дампы спасал connect under reset) — это НЕ флейк клона OB;
* для отладки ЗАПУЩЕННОГО приложения служит образ
  **`SM2Pro_full_flash_2.22.3_patched_v2_SWDON.bin`** (v6): тот же
  patched_v2, но команда по адресу 0x0800E1C пропатчена
  `orr #0x04000000` → `orr #0x02000000` (SWJ_CFG = 010: JTAG выкл,
  **SWD остаётся включён**; сборщик — `scripts/build_v6_swd_keep.py`).
  Бутлоадер перестаёт убивать SWD при LAUNCH — становятся возможны
  брейкпоинты, остановы и дампы RAM работающего приложения 2.22.3.

## 4. Прошивка образа

Вариант А — одной командой. Создайте файл `flash.jlink` рядом с образом:

```
loadfile SM2Pro_full_flash_2.22.3_patched_v2.bin,0x08000000
r
g
qc
```

и выполните (одной строкой):

```
"C:\Program Files\SEGGER\JLink\JLink.exe" -device STM32F105VC -if SWD -speed 4000 -AutoConnect 1 -CommanderScript flash.jlink
```

(старое имя опции: `-CommandFile flash.jlink`)

ВАЖНО: `r` и `g` обязательны — без них после прошивки ядро останется
остановленным и прибор будет выглядеть «мёртвым» до перетыка питания.

Вариант Б — J-Flash Lite (GUI): выбрать Device `STM32F105VC`, interface
SWD, открыть .bin, адрес **0x08000000**, нажать PROG. После прошивки
питание прибора переткнуть.

Вариант В — интерактивно в JLink.exe после `connect`:

```
JLink> loadfile SM2Pro_full_flash_2.22.3_patched_v2.bin,0x08000000
JLink> r
JLink> g
JLink> qc
```

Прошивка полного образа 256 КБ занимает ~10–30 секунд (loadfile сам
стирает нужные сектора). Откат на рабочую 2.21.35 — та же команда с
`firmware/fw_22135.bin`. **Option Bytes и RDP не трогать** (в J-Flash Lite
их и нет — не переходите в полный J-Flash без необходимости).

## 5. РЕШАЮЩИЙ ЭКСПЕРИМЕНТ: дамп зависания

Прибор после ошибки на экране остаётся «зависшим» под питанием — ядро
крутится (в вечном цикле крипто-ядра или в обработчике отказа). Но SWD в
этом состоянии МЁРТВ — бутлоадер отключает его при LAUNCH (раздел 3а):
живое подключение всегда даёт «Failed to initialize DAP». Дамп снимается
только через **connect under reset** (провод NRST): J-Link сам уходит в него
после провала живого подключения, останавливает ядро на векторе сброса и
видит **PC сброса** (точный PC зависания при этом теряется, но SRAM
переживает сброс — состояние зависания читается из дампа RAM).
Скрипт: `scripts/dump_hang.jlink` (аналог openocd-скрипта
`scripts/dump_hang.cfg`). Именно так были сняты дампы прогонов A/B.

### Прогон A — зависание в крипто-ядре (главный)

1. Прошить `SM2Pro_full_flash_2.22.3_patched_v2.bin` (раздел 4),
   питание прибора переткнуть.
2. Подключить провода OB (если не подключены).
3. Запустить ПК-программу Scanmatik 2.22.3, дождаться ошибки
     «Внутренняя ошибка микропрограммы 00000» (это и есть момент:
     приложение 2.22.3 вошло в крипто-ядро и не вернулось).
4. **Не выключая питание и не перетыкая USB прибора**, выполнить:

   ```
   "C:\Program Files\SEGGER\JLink\JLink.exe" -device STM32F105VC -if SWD -speed 1000 -AutoConnect 1 -CommanderScript dump_hang.jlink
   ```

5. Скрипт остановит ядро, выведет регистры (pc/sp/lr), регистры
   отказов, таблицу VM и сохранит `hang_dump_log.txt` + `hang_ram.bin`
   (полный дамп RAM 64 КБ) в текущую папку.
6. Питание прибора переткнуть (зависание сбросится).

### Прогон B — смерть после AUTH (автономная точка)

1. Прошить `SM2Pro_full_flash_2.22.3_AUTH_BYPASS.bin`, питание
   переткнуть.
2. Запустить smwin 2.22.3: на этот раз AUTH ответит (за миллисекунды),
   на экране будет **другая** ошибка — **сфотографируйте её точный код!**
   Через ~0,6 с приложение умирает полностью (адаптер исчезает из
   драйвера). Это и нужно: ядро остановлено в точке смерти.
3. Не выключая питание — тот же запуск `dump_hang.jlink` (файлы
   лога/RAM лучше переименовать, например `hang_B.log`/`hang_B.bin`,
   чтобы не затереть прогон A).
4. Питание переткнуть.

Прислать: `hang_dump_log.txt` и `hang_ram.bin` от обоих прогонов (Google
Drive, как обычно) + фото экрана с кодом ошибки из прогона B.

### Что покажут дампы (интерпретация)

* **pc в диапазоне 0x0800C15C–0x0800CED4** — вечный цикл VM-интерпретатора
  крипто-ядра. Таблица VM из дампа (0x2000D05C) расшифровывается офлайн:
  станет видно, каких данных ждало ядро (подтверждение/опровержение
  гипотезы «новое поколение бутлоадера»), и можно будет сделать точечный
  патч цикла.
* **pc = 0x08015CE4 (HardFault) или 0x080142D8 (BusFault)** — падение в
  отказ: регистры CFSR/HFSR из лога укажут команду-виновника.
* **pc в init-коде железа** — проблема специфична клон-плате.

## 6. Бонус-прогон A2: время работы крипто-ядра и середина VM

По дампам прогонов A/B (см. `docs/HANGDUMPS_ANALYSIS.md`) установлено:
ядро 0x0800C15C в прогоне A **запускалось и возвращало управление**, но
работает, по-видимому, секунды (≈3–4 с), тогда как драйвер ждёт ответ AUTH
только 1,4 с — отсюда «молчание» и «00000». Бонус-прогон доказывает это
и снимает состояние VM в середине работы.

Подготовка: прибор прошит `SM2Pro_full_flash_2.22.3_patched_v2_SWDON.bin`
(раздел 4; v6 — обязательно: в обычном patched_v2 SWD умирает в момент
LAUNCH и весь план неосуществим, см. раздел 3а), питание переткнуто,
smwin НЕ запущен (прибор в idle бутлоадера). Рядом с консолью
JLink держите часы/секундомер.

### 0) Если ловушка не сработала: «CPU is not halted» / «Could not read memory»

Сначала проверить, что ловушка ДЕЙСТВИТЕЛЬНО не сработала: попадание в
ловушку НЕ сопровождается никаким сообщением JLink — CPU просто молча
останавливается (светодиод гаснет, smwin показывает «00000» по таймауту —
это ожидаемое состояние T0, см. шаг 2). Проверка: `regs` → если печатает
регистры и PC = 0x0800C15C — всё СРАБОТАЛО, это успех (продолжать с шага
2, сохранив core_entry.bin). «Не сработала» — это когда `regs` отвечает
«CPU is not halted» или команды падают.

Главная причина (найдена реверсом, раздел 3а): **бутлоадер убивает SWD в
момент запуска приложения** (LAUNCH). Если smwin запускался хотя бы раз —
прибор в пост-LAUNCH состоянии, SWD мёртв, и ЛЮБЫЕ команды J-Link падают:
«Could not read memory», «Failed to initialize DAP», «CPU is not halted».
Так было во всех прежних попытках (и в логах дампов A/B живое подключение
не проходило никогда — только connect under reset).

**(а) Оживить SWD:** переткнуть питание прибора и НЕ запускать smwin —
прибор окажется в простое бутлоадера, SWD жив. Проверка:

```
JLink> mem32 0x08000000, 4     <- 20001800 0800032D ... — вектора: SWD+флеш ОК
JLink> mem32 0x20000000, 4     <- RAM (должен читаться)
JLink> mem32 0x0800728E, 1     <- какая прошивка в приборе (см. (б))
```

Если RAM читается, а флеш нет — активен RDP уровня 1 (раздел 7: защиту
НИКОГДА не снимать — unlock = полное стирание флеша). Если не читается
и RAM — провода/скорость/питание.

Для отладки ЗАПУЩЕННОГО приложения обычные образы не годятся (SWD умирает
на LAUNCH): прошить `SM2Pro_full_flash_2.22.3_patched_v2_SWDON.bin`
(раздел 3а) и только потом переходить к шагу 1.

**(б) Какая прошивка в приборе** (команда — только в простое бутлоадера,
см. (а)). Если после прогона B остался `AUTH_BYPASS`, то вызов ядра в нём
вырезан (`movs r0,#0; nop` на месте `bl` @0x0800728E; вызов ядра во всём
приложении ровно один) — ядро не вызывается вообще, и ловушка на входе
0x0800C15C сработать не может в принципе:

```
JLink> mem32 0x0800728E, 1
```

* `FF65F004` — вызов ядра на месте (patched_v2/official/SWDON): прошивка
  верная, проблема в ловушке → (г);
* `BF002000` — AUTH_BYPASS: перепрошить
  `SM2Pro_full_flash_2.22.3_patched_v2_SWDON.bin` (раздел 4), переткнуть
  питание, начать шаг 1 заново. (Косвенный признак: «smwin висит
  намертво» — картина B; на patched_v2 без ловушки smwin за ~15 с
  выдал бы привычную «00000», 3 цикла по ~5 с.)

**(в) Где ядро сейчас** (актуально, когда SWD жив — idle бутлоадера или
прошит SWDON):

```
JLink> h
JLink> regs
```

Расшифровка PC:
* `0x0800C15C–0x0800CED4` — крипто-ядро работает прямо сейчас: сразу
  снимать `regs` + `savebin` (это готовая «середина VM» из шага 5);
* `0x080010B3 / 0x0800225F / 0x080022E4` (машина состояний приёмника) —
  картина прогона B → в приборе AUTH_BYPASS (см. (б));
* `0x080009E6 / 0x080011FD / 0x080018AD / 0x080014E9 / 0x08000CF7`
  (отправка, ожидание IN-endpoint) — картина прогона A: ядро уже
  вернулось, приложение висит в отправке;
* `0x0800B99E / 0x0800B9A6` — главный цикл приложения жив, AUTH ещё не
  приходил (smwin до AUTH не дошёл);
* низкие адреса загрузчика (`0x080003xx`–`0x080005xx`) — был сброс
  (connect under reset), прогон сорван — начать заново.

**(г) Встала ли ловушка (FPB).** В J-Link Commander команды называются
`SetBP` / `ClrBP` (НЕ «SetBreakPoint»), аргумент один — адрес:
`SetBP 0x0800C15C` (без «H»; на Cortex-M это всегда аппаратная точка
FPB, слотов 6 — лог подключения уже показал «FPUnit: 6 code slots»).
Проверка фактической установки:

```
JLink> h
JLink> SetBP 0x0800C15C
JLink> mem32 0xE0002000, 1    <- FP_CTRL: бит 0 (ENABLE) должен быть 1
JLink> mem32 0xE0002008, 6    <- FP_COMP0..5: должно появиться 0x0800C15D
```

Кодировка FP_COMP (FPBv1): `FP_COMP = (адрес & 0x1FFFFFFC) | 1`, и если
целевой адрес — ВЕРХНЕЕ полуслово слова (бит 1 адреса = 1) — ещё
`| 0x40000000` (REPLACE=01). Контрольные значения: вход ядра 0x0800C15C
(нижнее полуслово) → **0x0800C15D**; возврат 0x08007292 (верхнее
полуслово слова 0x08007290) → **0x48007291**.

Если после SetBP в FP_COMP пусто — вероятная причина: внутренний слот
J-Link занят СТАРОЙ точкой, стёртой через w4 в обход Commander (регистры
обнулили, а Commander про неё помнит и молча не ставит новую).
Лечится освобождением слота и повтором:

```
JLink> ClrBP 0                     <- освободить внутренний слот 0
JLink> SetBP 0x08007292
JLink> mem32 0xE0002008, 6         <- контроль: 0x4800729x в FP_COMP0
```

Совсем вручную (нужен только `w4`):

```
JLink> w4 0xE0002008, 0x0800C15D    <- компаратор 0 = вход ядра 0x0800C15C
JLink> w4 0xE0002000, 0xC5AC0001    <- FP_CTRL: ключ 0xC5AC + ENABLE=1
JLink> mem32 0xE0002008, 6          <- контроль
```

Снять точку: `w4 0xE0002008, 0`. Ручное значение для возврата из ядра:
`w4 0xE0002008, 0x48007291` (REPLACE=01: адрес 0x08007292 — верхнее
полуслово слова 0x08007290).

**(д) Порядок прогона.** Ловушка ставится ДО запуска smwin, на
простаивающем приборе (сразу после перетыка питания). Если при connect
в логе мелькнуло «Failed to initialize DAP» / «Trying connect under
reset» — J-Link СБРОСИЛ прибор, состояние потеряно: переткнуть питание
и начать шаг 1 заново.

**(е) Запасной путь без ловушки** (только с SWDON-образом). Ядро работает
секунды (≈3–4 с), окно огромное: пустить smwin, через ~1 с `h` + `regs` —
PC окажется внутри ядра (готовая середина VM из шага 5). N оценивается
поллингом: `g` → пауза ~1 с → `h` → `regs`, пока PC не выйдет из диапазона
ядра. С обычным образом это НЕ работает: после LAUNCH SWD мёртв (3а).

### Шаг 1 — запуск и ловушка на входе ядра

Запустить JLink.exe (без параметров) и ответить на вопросы:
Device = `STM32F105VC`, If = `SWD`, Speed = `1000`, затем:

```
JLink> h
JLink> SetBP 0x0800C15C
JLink> mem32 0xE0002008, 6     <- контроль: в FP_COMP должно быть 0x0800C15D
JLink> g
```

(CPU остановлен, ловушка на входе в крипто-ядро установлена, CPU пущен.
Если SetBP точку не ставит — ручной вариант в «0(г)».)

### Шаг 2 — запуск smwin и остановка на входе ядра

Запустить smwin 2.22.3 и подключиться к адаптеру. Цепочка INFO → ARM →
LAUNCH → AUTH выполнится за доли секунды, и CPU встанет **на входе в
крипто-ядро** (PC = 0x0800C15C).

**ВАЖНО: JLink Commander НЕ печатает никакого сообщения о попадании в
ловушку** — CPU просто останавливается молча. Признак успеха — `regs`
показывает PC = 0x0800C15C. Побочные эффекты остановки (все — ОЖИДАЕМЫ,
это и есть состояние T0): светодиод прибора гаснет (приложение
остановлено), smwin через 1,4 с показывает «00000» (USB-поллинг замер →
таймаут драйвера). Это не сбои.

**Зафиксировать время (T0) или запустить секундомер.** Снять аргументы
ядра:

```
JLink> regs
```

Расшифровка (сверено с живым дампом и статикой AUTH-обработчика
0x0800722C):

| Регистр | Значение (пример) | Что это |
|---|---|---|
| PC | 0x0800C15C | вход в крипто-ядро (первая инструкция ещё НЕ исполнена) |
| LR | 0x08007293 | возврат в AUTH-обработчик после `bl` @0x0800728E |
| R0 | 0xA103DF88 | **аргумент 1**: слово челленджа (байты payload[0x28..0x2B] из 172-байтового AUTH) — меняется каждую сессию |
| R1 | 0x2000FD58 | **аргумент 2**: буфер ответа (0x138 Б на стеке AUTH-кадра; SP тот же) |
| R2 | 0x20000360 | **аргумент 3**: указатель челленджа (payload, выровненный вниз) |
| R3 | 0x40012C00 | НЕ аргумент: мусор от предыдущего кода (база TIM1; обработчик r3 не пишет) |
| R4/R6 | 0x2000035E / 0x20000362 | сообщение AUTH / payload (r6 = r4+4) |
| R9/R10 | 0x0800722D / 0x0800BF68 | живые регистры диспетчера (обработчик / таблица команд) |
| SP | 0x2000FD58 | база кадра AUTH (совпадает с разбором дампов A/B) |

Сразу сохранить базовое состояние RAM (челлендж в 0x20000360, ключи сессии
в кадре AUTH — материал для офлайн-декодирования VM):

```
JLink> savebin core_entry.bin, 0x20000000, 0x10000
```

### Шаг 3 — измерение времени работы ядра

Переставить ловушку с входа на возврат из ядра и пустить CPU:

```
JLink> ClrBP 0                    <- handle из ответа SetBP (или w4 0xE0002008, 0)
JLink> SetBP 0x08007292
JLink> mem32 0xE0002008, 6         <- контроль: в FP_COMP должно быть 0x4800729x
JLink> g                          <- СЕКУНДОМЕР С ЭТОГО МОМЕНТА (T0)
```

(ручной FPB-вариант: снять `w4 0xE0002008, 0`, поставить
`w4 0xE0002008, 0x48007291` и `w4 0xE0002000, 0xC5AC0001`.)

Примечания:

* остановка на входе НЕ искажает время работы ядра: halt случился ДО
  первой инструкции ядра, после `g` ядро стартует с чистого листа — любые
  внутренние проверки времени (если есть) начнут отсчёт сами;
* smwin к этому моменту уже показал «00000» — не важно: ядро — чистая
  арифметика и вернётся на 0x08007292 независимо от хоста; если драйвер
  успел перезапустить цикл — ловушка сработает на первом же возврате;
* суффикс H в `SetBP 0x0800C15C H` безвреден (hardware — и так единственный
  тип точек на Cortex-M).

**Засечь время.** CPU остановится на 0x08007292 (первая инструкция после
`bl` — вызова ядра) через N секунд — зафиксировать N (T1−T0). Снять
результат:

```
JLink> regs
```

r0 = возвращённое ядром значение (0 = успех, ответ собран; 6 = ошибка).

### Шаг 4 — дамп на выходе

```
JLink> savebin core_exit.bin, 0x20000000, 0x10000
JLink> ClrBP 1                     <- handle из ответа SetBP (или w4 0xE0002008, 0)
JLink> qc
```

(далее приложение, вероятно, зависнет в отправке — изученный случай;
питание переткнуть.)

### Шаг 5 — середина работы ядра (горячая точка VM)

Переткнуть питание прибора (прошивка та же). Повторить шаги 1–2 (ловушка
на входе, запуск smwin, останов на 0x0800C15C, T0). Затем пустить БЕЗ
второй ловушки и остановить по таймеру в середине работы ядра:

```
JLink> ClrBP 0                     <- handle из ответа SetBP (или w4 0xE0002008, 0)
JLink> g
(подождать примерно N/2 секунд)
JLink> h
JLink> regs
JLink> savebin core_mid.bin, 0x20000000, 0x10000
JLink> qc
```

PC из `regs` = горячая точка VM-интерпретатора; вместе с VM-таблицей
0x2000D05C и кадром ядра в RAM — материал для офлайн-декодирования VM.
Вариант совсем без ловушки (ядро работает секунды): запустить smwin,
через ~1 с `h` + `regs` + `savebin` — PC уже внутри ядра.

### Что прислать

1. Время N (сек) и возвращённое r0.
2. Текст `regs` всех остановок (вход / возврат / середина).
3. `core_exit.bin`, `core_mid.bin` (и `core_entry.bin`, если делали).

### Возможные сложности

* Если при подключении `Failed to initialize DAP` → connect under reset —
  состояние теряется: переткнуть питание и начать шаг 1 заново. Для живой
  сессии (прибор в idle) подключение обычно проходит с первой попытки.
* Если ловушка 0x08007292 не сработала за ~10 с — smwin, возможно, успел
  перезапустить цикл (INFO/ARM/LAUNCH перезапускают приложение, ядро
  будет вызвано снова) — оставить CPU запущенным: ловушка сработает
  на следующем вызове ядра.
* Пока CPU стоит на ловушке, USB не отвечает — smwin покажет свою ошибку
  ожидания; циклы перезапуска дают повторные попытки.
* `regs` отвечает «CPU is not halted» — ловушка не сработала; разбор в
  «0)» начала этого раздела (прошивка по 0x0800728E, FPB по 0xE0002008).

Дополнительные ловушки на отказы (по желанию, до запуска smwin):
`SetBP 0x08015CE4` (HardFault), `SetBP 0x080142D8` (BusFault),
`SetBP 0x0800892C` (NMI), `SetBP 0x08009280` (UsageFault). Всего FPB-слотов
6, так что вход ядра + 4 отказа помещаются.

## 7. Безопасность

* **Option Bytes / RDP не трогать.** Флеш через SWD ещё ни разу не читался
  (все чтения дампов A/B — RAM+PPB; полные дампы флеша снимались через
  USB-бутлоадер), так что состояние RDP НЕИЗВЕСТНО. Проверка (в простое
  бутлоадера, после перетыка питания): если RAM читается, а флеш нет —
  активна защита уровня 1. НИКОГДА не «снимать» её через J-Link/J-Flash/
  OpenOCD (unlock = массовое стирание флеша).
* `fw_22135.bin` — эталон отката: при любых странностях прошить его
  (раздел 4), прибор гарантированно возвращается в рабочее 2.21.35.
* Не питать прибор от OB, не соединять 5 В, общий GND обязателен.
* Не выполнять «erase chip» полным J-Flash — достаточно loadfile,
  который стирает только нужные сектора.
* Все действия — на свой риск.

## 8. Шпаргалка команд J-Link Commander

| Команда | Действие |
|---|---|
| `connect` | подключиться (спросит Device/If/Speed, если не заданы опциями) |
| `h` / `g` | остановить / пустить ядро |
| `r` | сброс (после него ядро стоит — нужен `g`) |
| `regs` | все регистры ядра (pc, sp, lr, r0-r12, xpsr) |
| `mem32 <адрес>, <кол-во>` | прочитать слова (напр. `mem32 0x08000000, 4`) |
| `w4 <адрес>, <значение>` | записать слово (напр. `w4 0xE0002008, 0x48007291`) |
| `savebin <файл>, <адрес>, <размер>` | сохранить область памяти в файл |
| `loadfile <файл>,<адрес>` | прошить образ (bin/hex/mot/S-рек) |
| `SetBP <адрес>` / `ClrBP <handle>` | аппаратная ловушка (FPB, до 6 шт.; НЕ «SetBreakPoint») |
| `sleep <мс>` | пауза в скрипте |
| `qc` | выйти |

Разделитель аргументов — запятая (пробел в большинстве версий тоже
принимается). В скриптах допустимы комментарии `//`.
