# Протокол 2.22.3: PID-выбор режима, команда авторизации 0x103, EEPROM-таблица

> Дополнительная линия анализа (дополняет JLINK_OB_GUIDE и APIMON-разборы):
> почему ПО Scanmatik 2.22.3 молчит с клоном на 2.22.3 (PID 0001), как ПО выбирает
> протокол, что именно проверяет авторизация и где лежит крипто-таблица.
> Источники: pcapng-сниффы (sm2pro2.21.35.pcapng / sm2pro .pcapng), трейсы API Monitor,
> smndis.sys/smndis.inf, дистрибутивы 2.21.32/2.21.35/2.22.3, слитый firmware.bin.

---

## 1. Драйвер smndis.sys: имя устройства = функция от PID

`Driver_NDIS/smndis.sys` (PDB: `X:\sm3\_DriverNDIS\Release\smndis.pdb`) регистрирует
два шаблона DOS-имён:

```
\Device\SmUsbNNN            → \\.\SmUsb000            — для PID 0x0001 (старая ревизия)
\Device\SmUsb_PID_XXXX_NNN  → \\.\SmUsb_PID_0002_000  — для PID 0x0002 (новая ревизия)
```

`smndis.inf` биндит оба PID (`USB\VID_20A2&PID_0001` и `PID_0002`).
USB-дескриптор (EP1 IN + EP2 OUT bulk, класс ff) задаёт **bootloader** @0x0800271A
(в дампе клона PID = **0x0001**, bcdDevice 0x0100).

**Следствие:** Sm2Lib/PlxLib выбирает ветку протокола по тому, какое имя открылось:

| Конфигурация | Что открывает ПО | Поведение |
|---|---|---|
| PID 0001 + прошивка 2.21.35 | `\\.\SmUsb000` | СТАРЫЙ протокол — работает (см. §2) |
| PID 0001 + прошивка 2.22.3 | `\\.\SmUsb000` | ПО пробует старый протокол → **0 BOT-команд, тишина** |
| PID 0002 + прошивка 2.22.3 | `\\.\SmUsb_PID_0002_000..009` | НОВЫЙ протокол (гипотеза, проверяется прогоном v2) |

> УТОЧНЕНИЕ (по повторному разбору transcript_authbypass.txt): прогон AUTH_BYPASS
> шёл по СТАРОЙ ветке — успешный open `\\.\SmUsb000` в t=0, обмен 0x86→0x83→0x88→
> 0x37→0x12→248Б. Строки `SmUsb_PID_0002_000..009` в t≈72 с — это НЕУДАЧНЫЙ
> (ret=0, err=2) sweep поиска пропавшего устройства, а не новая ветка.
> Ошибка «54А14094» в том прогоне — реакция ПК на мусорный ответ AUTH по старой
> ветке. Ветка PID 0002 живьём ещё не проверялась.

## 2. USB-сниффы: рабочая сессия vs провал

Формат USBPcap: заголовок bulk 27 байт, данные с 0x1B; control 28 байт + setup.
Адаптер = VID 0x20A2 (в сниффах различаем по device-descriptor).

**sm2pro2.21.35.pcapng (РАБОТА, 2.21.35 на клоне):**
- Enumeration адаптера (ff/00/00, EP1 IN 64b + EP2 OUT 64b), SET_CONFIG;
- BOT-хартбит каждые ~0.75 с: `TEST_UNIT_READY` → CSW status=1 (CHECK CONDITION)
  → `REQUEST_SENSE` → sense `02/3A` (NOT READY / NO MEDIUM) — 45 пар за сессию;
- Постоянный поллинг EP1 IN (~200 Гц): 8-байтовые кадры статусов каналов
  `00 CC SS 00 CC 00 SS 00`, CC=3..6, SS=1..2 (каналы активны);
- Диагностических команд в сниффе НЕТ (сессия снята в простое — нужен повторный
  снифф при реальной диагностике, см. CLAUDE_LINK_PROMPT Этап 3).

**sm2pro .pcapng (ПРОВАЛ, 2.22.3 на клоне):**
- Enumeration идентичен (тот же дескриптор!), SET_CONFIG;
- **Ноль BOT-команд** — ПО открыло `\\.\SmUsb000`, не получило ожидаемого от
  старого протокола и замолчало;
- Поллинг EP1 IN (~330 Гц): кадры `00 01 00 00 01 00 00 00` / `00 02 00 …`
  (каналы 1–2, статус 0) — прошивка 2.22.3 жива, но шлёт данные нового формата.

**AUTH_BYPASS (API Monitor):** ПО перебирает `\\.\SmUsb_PID_0002_000..009`
(строки в data-логе) — начало новой ветки протокола; итог — ошибка 29CD744C.

## 3. Архитектурное различие 2.21.x vs 2.22.3

| | 2.21.32 / 2.21.35 (дистрибутивы) | 2.22.3 (слитая firmware.bin) |
|---|---|---|
| Приложение @0x08005000 | **без векторной таблицы** (код с 1-го байта) | **с VT** (SP=0x2000FF30, Reset=0x08005165) |
| Модель | stage2 = резидентное ядро (вектора 0x08004169+), приложение = плагин | самодостаточное приложение; stage2 = только флешер (вектора 0x08004165+) |
| Обращения к сервисам bootloader ([0x0800017C]) | **0** | **5 точек**: 0x08007248 (svc7), 0x08007E82/0x08007EE2/0x08007F0A (svc5/6, команда 0x103), 0x0800B816 (svc10) |

Прямого совпадения кода приложений нет ни при каких сдвигах → firmware.bin
действительно 2.22.3 (слитая после OTA), а не конверсия 2.21.35.

## 4. Авторизация 2.22.3: команда 0x103 и крипто-таблица EEPROM

Обработчик — **0x08007E60** (та самая зона, чей вызов из AUTH-кластера G/0x0800722C
через `bl 0x0800728E` ведёт в ядро 0x0800C15C — см. JLINK_OB_GUIDE):

```c
int cmd_0x103(pkt *fp) {               // [fp+1](u16) == 0x103
    if (fp->mode == 0x00) {            // ЧТЕНИЕ
        fp->f5 = eeprom_read(0x38);
        for (i=0;i<128;i++) fp->table[i] = eeprom_read(0x39+i); // regs 0x39..0xB8
        return 0;
    }
    if (fp->mode == 0x99) {            // ЗАПИСЬ + ВЕРИФИКАЦИЯ
        eeprom_write(0x38, fp->f5);
        for (i=0,mis=0;i<128;i++) {
            if (eeprom_read(0x39+i) != fp->table[i]) {
                eeprom_write(0x39+i, fp->table[i]);
                if (write_failed) return 6;
                mis++;
            }
        }
        return mis ? 0x20 : 0;         // 0x20 = верификация провалена
    }
    return 1;
}
```

Сервисы 5/6 bootloader — это **НЕ внешний чип**, а EEPROM-эмуляция во внутренней
flash (0x08001AF6/0x08001B1C):
- страница A @0x08002800 (магия **0x5AA5** @0x08002FFE) / страница B @0x08003000;
- чтение — из активной страницы; запись halfword'ами; если ячейка != 0xFFFF —
  уходит в запасную страницу (зеркало ±0x800).

**Таблица авторизации** (128×16 бит, регистры 0x39–0xB8 → физически
0x08002872–0x08002970):

| Образ | Таблица |
|---|---|
| SM2_2.21.35_A71283.bin | **ЗАПОЛНЕНА** (рег. 0x60–0xA7, физически 0x28C0–0x294E: `23da 3112 1223 2331 …`) |
| SM2_2.21.32_A111788.bin | пустая (0xFFFF) |
| firmware.bin (2.22.3, клон) | **пустая + мусорные не-0xFFFF остатки** (`f69e 3247`, `43ff`, `353c 0001 …`) |

**ВАЖНО — перекрытие слотов и таблицы.** Формула EEPROM-сервиса подтверждена
дизассемблером (read @0x08001AF6, write @0x08001B1C): физический адрес = база
активной страницы + N·2. «Слоты 3–8» = регистры 0x43–0x48 = 0x08002886–0x08002891 —
это ВНУТРИ региона таблицы (regs 0x39–0xB8). У рабочего 2.21.35 эти ячейки пустые
(старый стаб их не использует), у образов 2.22.3 они обязаны содержать
{size=0x0001353C, ver=0x00001198, crc=0x210E9A13} — обработчик LAUNCH (0x37)
стаба 2.22.3 (@0x08004416, читалка слотов @0x08004604: svc5 по regs 7,8→crc,
5,6→ver, 3,4→size) сверяет их с пакетом; при несовпадении возвращает **7** →
экранная ошибка **[0007]**, приложение НЕ запускается. Поэтому при копировании
таблицы из 2.21.35 слоты нужно вернуть вручную — у подлинного прибора,
обновлённого OTA на 2.22.3, страница A выглядит именно так: таблица 2.21.35 +
слоты LAUNCH 2.22.3.

Мусорные остатки критичны: при 0x99-записи прошивка читает из активной страницы A,
видит не-0xFFFF → уводит запись в страницу B, а чтение остаётся из A → верификация
`(read != expected)` не сходится → `return 0x20` → ПО показывает
«Внутренняя ошибка микропрограммы 29CD744C» (код вычисляемый, в прошивке
константой отсутствует).

Первые 16 регистров EEPROM (0x08002800–0x0800281F) — метаданные загрузки
(CRC stage2/длина; проверяются в cmd-probe @0x080011A8:
CRC32(0x08004000, len/4) == reg[0]). firmware.bin: `9a13 210e | 1198 0000 | 353c 0001`;
2.21.35: `e2cd 01e9 | 1096 0000 | b5ec 0000`.

## 5. Связь с ядром challenge-response (из JLINK_OB_GUIDE)

Кластер 0xAC (G @0x0800722C) берёт build ID (svc7) и 3 ключа (svc8,
таблица 0x08000184+) и вызывает ядро 0x0800C15C (F) с сигнатурой:
`r0 = challenge payload[0x28..0x2B]`, `r1 = буфер ответа 0x138 Б`, `r2 = ptr challenge`.
Таймаут ядра ~1.4 с → «00000». Логично, что 248 Б «верификации» из APIMON-разборов
(ошибка 54A14094 у старого бутлоадера) — это и есть пакет 0x103 (таблица 128×16=256 Б
+ заголовок), который требует новая прошивка, а 0x103-обмен идёт через EEPROM-таблицу
и ключи. Полная цепочка: ПО → 0x103 (таблица) + 0xAC (challenge на ключах) → ядро.

## 6. Готовые патчи-кандидаты (patched/) — v2, пересобраны

> ИСПРАВЛЕНО ДВЕ ОШИБКИ ПЕРВОЙ СБОРКИ:
> 1) PID писался на 0x08002724 — а это ЗАГОЛОВОК КОНФИГ-ДЕСКРИПТОРА
>    (`09 02` = bLength 9, bType 2; USB-стек передаёт confdesc = 0x08002712+0x12
>    — см. код @0x080019A2, литерал 0x080019D0). Старый патч ломал перечисление
>    USB и НЕ менял реальный PID. Правильное место — **idProduct @0x0800271C**
>    (device-дескриптор начинается @0x08002712: `12 01 00 02 ff 00 00 40 | a2 20 |
>    01 00 | 00 01 …`).
> 2) При копировании таблицы из 2.21.35 стирались слоты LAUNCH 0x2886–0x2891
>    (перекрытие, см. §4) → стаб вернул бы 7 → [0007]. Теперь слоты возвращены.

## 7. Что осталось проверить живьём (CLAUDE_LINK_PROMPT.md — упрощённый вариант)

1. Залить `firmware/SM2Pro_full_flash_2.22.3_AUTH_TABLE+PID2_v2.bin`, поставить
   BP 0x08007E60 (вход обработчика 0x103) и 0x08007F50 (конец ветки записи);
2. Запустить ПО Scanmatik 2.22.3 → на каждой остановке снимать regs + дамп
   0x120 Б от R0 (пакет: [R0+1]=0x103, [R0+4]=режим 0x00/0x99, [R0+5]=слово
   reg0x38, [R0+7..]=таблица 128×16) + полный RAM;
3. Зафиксировать реакцию ПО (код экранной ошибки) на каждый прогон;
4. Если остановок нет — ram_idle.bin и дальше точка на диспетчер сообщений
   приложения;
5. Повторный USBPcap при РЕАЛЬНОЙ диагностике на 2.21.35 — полный словарь команд
   старого протокола (в текущем сниффе только хартбит).
