# Анализ ошибки «Внутренняя ошибка микропрограммы 00000» (после v2)

> **ОБНОВЛЕНИЕ (v2):** после отчёта «все тестовые образы дают 00000» выполнен
> глубокий реверс: архитектура связи 2.22.3 расшифрована полностью, гипотезы
> A/C сняты, собраны диагностические образы PROBE/MODE1. См.
> **`DIAGNOSTIC_PLAN_v2.md`** — актуальный план тестов и выводы. Ниже —
> исходный анализ для истории.

## Симптом

После заливки `SM2Pro_full_flash_2.22.3_patched_v2.bin` (исправленные
EEPROM-слоты 3–8 + загрузочная запись) прежняя ошибка
`[0007] Внутренняя ошибка микропрограммы адаптера (FLASH/MCU)` исчезла —
**прошивка 2.22.3 запускается** (команда 0x37 LAUNCH проходит проверку слов
идентификации). Вместо неё родная ПК-программа (smwin.exe, Scanmatik-2)
показывает:

```
Внутренняя ошибка микропрограммы 00000
```

Это **другая** ошибка и **другой этап**: прогресс есть, проблема сместилась
на обмен ПОСЛЕ запуска приложения.

## Откуда берётся текст «...00000»

Формат найден в `smwin.exe` (2.22.3, файл `new_dist/extracted/Scanmatik/`):

```
smwin.exe  file 0xA7E20: 'VCI firmware internal error %05lX'   (EN)
smwin.exe  file 0xA7E68: 'Внутренняя ошибка микропрограммы %05lX'  (RU)
```

`%05lX` — **шестнадцатеричный** код из 5 знаков. То есть устройство (или
тайм-аут) дало код **0x00000**. Строка лежит в парной таблице локализации
(EN/RU) smwin.exe, выбор — через `sm2lib_83 = GetString(entry)` (язык в
глобали `[0x1007c2c4]`). smwin.exe защищён (нативный .text + ~5 МБ
упакованных данных в .reloc, секция .fptable обнулена на диске), поэтому
точный вызов статически не трассируется, но семантика однозначна:
**код 0 = «приложение не ответило / ответило ошибкой без кода»**.

Для сравнения — таблица статусных кодов протокола (sm2ptconfig.exe 2.22.3,
jump-таблица 0x41838C, switch в функции 0x4181xx):

| Код | Текст |
|-----|-------|
| 0 | [0000] Операция успешно завершена |
| 1 | Неверный параметр |
| 2 | Превышено время отправки сообщения |
| 3 | Неверный ответ от блока управления |
| 6 | Операция завершена с ошибкой |
| 7 | Внутренняя ошибка микропрограммы адаптера (FLASH/MCU) |
| 9 | Нет связи с адаптером |
| 16 | Неверная длина ответа |
| 19/20 | Ошибка стирания/сравнения FLASH |
| 21 | Неизвестная ошибка |

«%05lX»-сообщение — НЕ из этой таблицы: это отдельный механизм smwin.exe для
**кода внутренней ошибки самой микропрограммы** (внутренний код прошивки,
вернуть который может только запущенное приложение — либо поле остаётся 0,
если ответа нет).

## Что происходит после 0x37 (установлено реверсом sm2lib.dll 2.22.3)

Сценарий подключения FUN_1000CD50 (экспорт sm2lib_49):

```
0x83 INFO (бутлоадер)  → serial 0x0A111788, ver (из загрузочной записи), type=2
записи обновления      → FUN_1000C760: {stub: seed 0x7821AB35, ver 0x1198,
                          size 0xB00, crc 0x2912D0A0; app: ver 0x1198,
                          size 0x1353C, crc 0x210E9A13}
ver(устройства)==0x1198 → обновление НЕ нужно (v2: загрузочная запись = 0x1198 ✓)
0x88 ARM               → запуск стаба 0x08004000 (отправляется всегда)
0x37 LAUNCH {ver,crc,size} → v2: слова совпали со слотами 3–8 ✓, state=2
                           → ответ {status=0} → стаб передаёт управление
                             приложению 0x08005000 (трамплин 0x08004190:
                             VTOR=0x08005000, MSP из вектора, cpsie i, bx r1)
return 0 — СЦЕНАРИЙ ПОДКЛЮЧЕНИЯ ЗАВЕРШЁН УСПЕШНО
```

Дальше smwin.exe ведёт обмен уже с приложением (через экспорты sm2lib:
открытие — sm2lib_45, информация — sm2lib_148 и т.д.). Именно на этом этапе
появляется «00000».

## Новое в 2.22.3 (отличия от 2.21.32, важно для диагноза)

1. **Аутентификация cmd 0x12 полностью переработана**: запрос 0xAC (172) байт
   вместо короткого challenge; ответ 0x134 (308) байт, включая 0x80 байт
   ключевого материала (смещение ответа 0xB4). Обработчик в приложении
   (0x080072xx) вызывает:
   - сервис бутлоадера 7 (серийный номер из 0x08000180),
   - сервис бутлоадера 8 (чтение dword из крипто-блоба 0x08000184+idx*4!),
   - обфусцированное ядро 0x0800C15C (именно оно читает «UID» из пула
     0x0800C520 — место, аналогичное слову 0x0800E958 в 2.21.32).

2. **Приложение 2.22.3 впервые использует сервисы бутлоадера** (в 2.21.32
   приложение вообще не ссылалось на таблицу [0x0800017C]): сервис 10 при
   старте (режим платы: донорский бутлоадер возвращает 2; режим задаёт
   таблицу пинов GPIO — для 2 и 3 таблица одна, отличие режима 3 — бит 0x80
   в регистре 0x4002103C, на STM32F105 это reserved/no-op), сервисы 5/6
   (чтение/запись EEPROM-слотов), сервисы 7/8 (серийник, ключи).

3. **Команда 0x27 (конфигурация, длина пакета 0x103)**: чтение (sub 0) /
   запись (sub 0x99) EEPROM-слотов 0x38–0xB8 (адреса 0x080028F0–0x080029F1),
   слот 0x38 — контрольная сумма блока. ПК **проверяет контрольную сумму**
   ответа. У донора эти слоты пусты (0xFF). Команду отправляет только
   smj2534.dll (J2534-драйвер), не sm2lib/smwin.

4. **Данные 0x8B (0x68 байт)** при обновлении этапа 1 — пишутся только если
   бутлоадер ответил 0x18/1 (новое поколение). Донорский бутлоадер 2.21.32
   команду 0x8B не поддерживает (tbb-таблица 0x80–0x8A). Для серийников из
   skip-списка (включая A111788) обновление и вовсе пропускается — значит,
   на «настоящем» A111788 эти данные появились при заводской прошивке.

5. Список «не обновлять» (27 серийников, XOR 0x33335555) содержит донорский
   A111788 — клон снят с внутреннего прибора Scanmatik.

## Рабочие гипотезы (по убыванию вероятности)

| # | Гипотеза | Комментарий |
|---|----------|-------------|
| B1 | Приложение 2.22.3 несовместимо со старым бутлоадером: новая схема cmd 0x12 использует ключи (сервис 8, блоб 0x08000184) или данные (0x8B/конфиг-слоты), которых на донорской связке нет; auth/инициализация завершается ошибкой либо приложение зависает в init (cpsid i … cpsie i) → ПК не получает ответ → код 0 | Подтверждается тем, что 2.21.32 приложение сервисов не вызывало вовсе |
| A | Наш патч 9 слов UID чрезмерен: в 2.21.32 донор патчил ОДНО слово, а мы заменили все 9 литералов; часть из них может обслуживать новые проверки 2.22.3, где чтение EEPROM вместо системного UID ломает логику | Все 9 слов — настоящие пулы литералов (ldr rX, [pc, #imm]) внутри одного обфусцированного ядра 0x0800C15C; семантика редиректа та же, что у донора |
| C | Приложение стартует, но первый ответ приходит позже тайм-аута ПК (длинный init 2.22.3) | Менее вероятно, но исключить нельзя |

## План экспериментов (изолируем переменные)

1. **Тест A — `SM2Pro_full_flash_2.22.3_patched_v3_minimal.bin`** (НОВЫЙ):
   патч UID только в auth-пуле 0x0800C520 (аналог донорского минимального
   патча 2.21.32), остальные 8 слов — оригинальные (аппаратный UID).
   - Ошибка изменилась/пропала → виноват широкий патч (гипотеза A).
   - Та же «00000» → патч не при делах, дело в бутлоадере/данных (B1).

2. **Тест B — `SM2Pro_full_flash_2.22.3_official_v2.bin`**:
   официальное приложение вообще без патча UID (EEPROM исправлен).
   - Любой результат сравнить с v2/v3: если «00000» осталась — патч точно
     ни при чём.

3. **Тест C — sm2ptconfig.exe из пакета 2.22.3**: его сообщения точнее
   (таблица кодов 0–21). Например:
   - «[0002] Превышено время отправки...» = приложение не отвечает (подтверждение B1/C — зависание);
   - «[0007]» на новом месте = приложение само отвечает кодом 7;
   - «[0009] Нет связи» = проблема транспорта.

4. **Тест D — откат для работоспособности**: `SM2Pro_full_flash_2.21.32_donor_asis.bin`
   + старое ПО 2.21.32 — прибор должен работать как раньше (проверка, что
   железо в порядке).

Если подтвердится B1 (старый бутлоадер несовместим с 2.22.3), варианты:
- искать дамп бутлоадера 2.22.3-поколения (с поддержкой 0x8B/новых сервисов)
  — в ПК-дистрибутиве его НЕТ (там только stub+app);
- остаться на 2.21.32 (стабильно работает с патчем клона);
- попытаться патчем приложения отключить новые проверки (сложно: код
  обфусцирован control-flow flattening, диспетчер состояний 0x0800C2CA с
  таблицей переходов 0x08010D7C).

## Технические детали для протокола

- Таблица сервисов бутлоадера (донор 2.21.32): count=14 @[0x080002E8],
  таблица @[0x080002EC]; диспетчер 0x080002CC: `if (opcode>=14) return 0`,
  иначе `table[opcode](arg)` и `return 1`.
  Сервис 10 = «режим платы»: `*(int*)arg = 2` (0x080012CE).
  Сервис 7 = серийный номер `*(0x08000180)` (0x080012C2).
  Сервис 8 = ключи: `*(0x08000184 + idx*4)` (0x080012D4).
- Приложение 2.22.3, вход 0x08005150: SP=0x2000FF30 → init 0x08006340 →
  main 0x0800B7F0: cpsid i → сервис 10 (режим) → таблица пинов
  (режим 1 → 0x08018338, режим 2/3 → 0x080183C9; режим 3 дополнительно
  `[0x4002103C] |= 0x80` — reserved-регистр, no-op на F105) →
  init-функции 0x800bc4c/0x8017660/0x800bcf0/0x800bd3c/0x801681c → cpsie i.
  Если любое из них зависнет — USB молчит (прерывания выключены) — ПК
  получит тайм-аут → «00000».
- Конфиг-область 2.22.3: EEPROM-слоты 0x38 (контрольная сумма) и 0x39–0xB8
  (0x100 байт, 64 big-endian dword) — команда 0x27 (len 0x103, sub 0/0x99),
  отправляется smj2534.dll; у донора область пуста (0xFF).
- smwin.exe импортирует только KERNEL32/USER32/GDI32/COMDLG32/SHELL32/
  **PlxLib.dll**/**Sm2Lib.dll**/COMCTL32/ADVAPI32. smj2534.dll грузится
  J2534-клиентами отдельно.
- Защита модулей: у всех файлов Scanmatik есть секция .fptable (32 нулевых
  указателя на диске — заполняется при загрузке), таблицы экспорта
  «испорчены» на диске (заголовок с мусором, массивы на месте),
  smwin.exe/sm2ptconfig.exe несут ~5 МБ упакованных данных в .reloc после
  валидных relocation-блоков.
