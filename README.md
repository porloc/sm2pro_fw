# SM2 Pro (Scanmatik 2 Pro клон) — анализ прошивки 2.22.3

> Отчёт по реверс-инжинирингу: почему китайский клон SM2 Pro (STM32F105VCT6) работает
> на прошивке 2.21.35, но не работает на 2.22.3. Инструменты: статический анализ
> (capstone), USB-сниффы (pcapng), трейсы API Monitor, дампы RAM через J-Link.

---

## 1. Железо и карта памяти

| Компонент | Значение |
|---|---|
| МК | **STM32F105VCT6** (Cortex-M3, 256KB flash, 64KB RAM) — подтверждено J-Link |
| USB | OTG FS @0x50000000, VID **0x20A2**, PID **0x0001** (клон) / **0x0002** (оригинал, новая ревизия) |
| USB-дескриптор | класс `ff/00/00`, EP1 IN bulk 64b + EP2 OUT bulk 64b — задаёт **bootloader** (0x0800271A) |

### Карта flash (256KB)
```
0x08000000  bootloader (12KB) — НЕ обновляется при OTA
            ├─ USB-стек (дескриптор @0x0800271A), BLE ("AT-AB -BypassMode-")
            ├─ 14 сервисов для приложения (таблица @0x080002EC, диспетчер 0x080002CC)
            ├─ ключи: [0x08000180]=build ID, [0x08000184+]=таблица ключей
            ├─ EEPROM-эмуляция: страница A @0x08002800 (магия 0x5AA5 @0x08002FFE),
            │   страница B @0x08003000 (зеркало/swap)
            └─ CRC32 (аппаратный, 0x40023000)
0x08004000  stage2 (4KB) — флешер/загрузчик (обновляемый)
0x08005000  приложение (~80KB, обновляемое)
0x08019000  стёрто
```

### Сервисы bootloader (вызов через указатель [0x0800017C] → диспетчер 0x080002CC)
| # | Назначение |
|---|---|
| 4 | программный рестарт (launcher 0x08000218 → VTOR → stage2) |
| 5 | **чтение EEPROM-регистра** (0x08001AF6): активная страница 0x08002800/0x08003000 по магии 0x5AA5 |
| 6 | **запись EEPROM-регистра** (0x08001B1C): halfword-программирование flash + запасная страница |
| 7 | build ID ([0x08000180]) |
| 8 | ключ [0x08000184 + idx*4] |
| 9 | CRC32 области flash (аппаратный) |
| 10 | boot reason |
| 13 | передача блока (обновление) |

## 2. Ключевое различие архитектур

| | 2.21.32 / 2.21.35 (дистрибутивы) | **2.22.3** (firmware.bin, слитая с адаптера) |
|---|---|---|
| Приложение @0x08005000 | **без векторной таблицы** (код сразу) | **с векторной таблицей** (SP=0x2000FF30, Reset=0x08005165) |
| Архитектура | stage2 = резидентное RT-ядро, приложение = плагин | самодостаточное приложение, stage2 только флешер |
| Вход приложения | через резидентный stage2 (вектора 0x08004169+) | `ldr sp,=…; bl init; bx 0x0800B7F1` (main @0x0800B7F0) |
| Вызовы сервисов bootloader | **0 обращений к [0x0800017C]** | **5 точек вызова** (см. ниже) |

Вывод: **2.22.3 — новая архитектура с новым протоколом связи с хостом**.
firmware.bin — именно 2.22.3 (слитая с адаптера после OTA-обновления), её код не совпадает
ни с 2.21.32, ни с 2.21.35 ни с каким сдвигом.

## 3. Почему ПО Scanmatik 2.22.3 не работает с клоном

### 3.1. Выбор протокола по PID (драйвер smndis.sys)
Драйвер `Driver_NDIS/smndis.sys` (PDB: `X:\sm3\_DriverNDIS\Release\smndis.pdb`) создаёт
DOS-имена устройств **по PID**:
```
\\.\SmUsb000            — PID 0x0001 (старая ревизия) → СТАРЫЙ протокол
\\.\SmUsb_PID_0002_NNN  — PID 0x0002 (новая ревизия) → НОВЫЙ протокол
```
(строки-шаблоны `\Device\SmUsbNNN`, `\Device\SmUsb_PID_XXXX_NNN` внутри smndis.sys;
`smndis.inf` биндит оба PID).

### 3.2. Что видно в трейсах

| Трейс | Устройство | BOT-команды (USBC) | Поллинг EP1 IN |
|---|---|---|---|
| `sm2pro2.21.35.pcapng` (РАБОТА) | 20A2:**0001** + прошивка 2.21.35 | 45 пар TEST_UNIT_READY/REQUEST_SENSE (хартбит, ответ 02/3A) | 4475 ответов: каналы 3–6, статусы 1–2 |
| `sm2pro .pcapng` (ПРОВАЛ) | 20A2:**0001** + прошивка 2.22.3 | **0** (ПО молчит) | 6585 ответов: каналы 1–2, статус 0 |
| `AUTH_BYPASS` (API Monitor, патч PID→0002) | 20A2:**0002** + прошивка 2.22.3 | — | ПО открыло `\\.\SmUsb_PID_0002_000..009`, начало НОВУЮ авторизацию → **«Внутренняя ошибка микропрограммы 29CD744C»** |

Сценарий провала на клоне (PID 0001 + 2.22.3): ПО открывает `\\.\SmUsb000`, пробует
старый протокол — новая архитектура 2.22.3 его не поддерживает → ПО не посылает
ни одной BOT-команды → «не работает».

Сценарий AUTH_BYPASS (PID 0002): ПО начинает новую авторизацию — и она падает
с кодом **29CD744C** (вычисляемый код; в прошивке отсутствует как константа).

### 3.3. Механизм авторизации 2.22.3 — команда 0x103

Обработчик в прошивке 2.22.3: **0x08007E60** (кластер команд 0x103):

```c
int cmd_0x103(pkt *fp) {              // [fp+1] = 0x103 (ID кластера)
    if (fp->mode == 0x00) {           // ЧТЕНИЕ
        fp->field_5 = eeprom_read(0x38);
        for (i = 0; i < 128; i++)     // 128 x 16bit
            fp->table[i] = eeprom_read(0x39 + i);   // регистры 0x39..0xB8
        return 0;
    }
    if (fp->mode == 0x99) {           // ЗАПИСЬ + ВЕРИФИКАЦИЯ
        eeprom_write(0x38, fp->field_5);
        mismatches = 0;
        for (i = 0; i < 128; i++) {
            v = eeprom_read(0x39 + i);
            if (v != fp->table[i]) {
                eeprom_write(0x39 + i, fp->table[i]);   // перезапись
                if (write_failed) return 6;
                mismatches++;
            }
        }
        if (mismatches > 0) return 0x20;   // ВЕРИФИКАЦИЯ ПРОВАЛЕНА
        return 0;
    }
    return 1;                          // неизвестный режим
}
```

**Крипто-таблица** (128×16 бит, регистры 0x39–0xB8 → flash 0x08002872–0x08002970):

| Образ | Состояние таблицы |
|---|---|
| `SM2_2.21.35_A71283.bin` | **ЗАПОЛНЕНА** (регистры 0x60–0x99: `23da 3112 1223 2331 4312 …`) |
| `SM2_2.21.32_A111788.bin` | пустая (0xFFFF) |
| `firmware.bin` (2.22.3 с клона) | **пустая (0xFFFF) + мусорные остатки** (`f69e 3247`, `43ff`) |

У клона таблица не инициализирована → ПО читает её (или не проходит запись/верификацию
из-за мусорных не-0xFFFF остатков в странице A, из-за чего записи уходят в запасную
страницу B, а чтения идут из активной A) → **«Внутренняя ошибка микропрограммы 29CD744C»**.

Рядом (G @0x0800722C, кластер 0xAC) авторизационные вычисления идут через
VM-интерпретатор F @0x0800C15C с ключами bootloader'а (сервисы 7/8) —
challenge-response с шифрованием. Полный протокол требует живой отладки.

### 3.4. EEPROM-страница и целостность

Первые 16 регистров EEPROM (0x08002800–0x0800281F) — метаданные: CRC stage2 и длина
(проверка в `cmd probe` @0x080011A8: CRC32(0x08004000, len) == reg[0]). У клона:
```
firmware.bin:  9a13 210e | 1198 0000 | 353c 0001   (CRC/длина/флаги для ЕГО stage2)
2.21.35:       e2cd 01e9 | 1096 0000 | b5ec 0000
```
При патче stage2/приложения контрольные слова должны соответствовать — иначе
bootloader откажется запускать (state-машина 0x080012F4).

## 4. Готовые патчи (экспериментальные)

| Файл | Что сделано |
|---|---|
| `patched/firmware_2.22.3_AUTH_TABLE.bin` | таблица авторизации 0x39–0xB8 скопирована из SM2_2.21.35_A71283 (PID остался 0001) |
| `patched/firmware_2.22.3_AUTH_TABLE+PID2.bin` | то же + **PID 0x0002** в дескрипторе bootloader'а (0x08002724) — ПО начнёт новый протокол |

Заливка (J-Link Commander):
```
J-Link> device STM32F105VC
J-Link> connect
J-Link> h
J-Link> loadfile firmware_2.22.3_AUTH_TABLE+PID2.bin, 0x08000000
J-Link> r
J-Link> g
```
Вариант щадящей заливки (не трогая bootloader): только изменённые страницы EEPROM —
записать диапазон 0x08002800–0x08002A00 (стересть страницу A, залить таблицу,
вернуть магию 0x5AA5 @0x08002FFE и исходные 16 регистров метаданных).

**Важно**: перед экспериментом сохранить текущий дамп:
```
J-Link> savebin backup_full.bin, 0x08000000, 0x40000
```

### Ожидаемые исходы
- `AUTH_TABLE` (PID 0001): скорее всего без изменений — ПО использует старый протокол,
  который 2.22.3 не поддерживает.
- `AUTH_TABLE+PID2`: ПО начнёт новую авторизацию. Если проверка ПО — только чтение
  таблицы → может пройти. Если challenge-response на ключах таблицы → вероятно,
  потребуется живая отладка (см. §5).

## 5. Что нужно для финального решения (живая отладка)

Через J-Link + Claude Code (MCP) на железе:

1. **Снять дамп рабочей диагностики**: залить 2.21.35, запустить диагностику в ПО
   Scanmatik 2.22.3, снять USBPcap-снифф — увидим ПОЛНЫЙ старый протокол команд
   (в текущем трейсе диагностики не было, только хартбит).
2. **BP на авторизации**: на патче PID2 поставить `SetBP 0x08007E60` (обработчик 0x103),
   запустить ПО, при останове снять `regs` + дамп буфера команды (R0 → структура
   [R0+1]=0x103, [R0+4]=режим, [R0+5..7+256]=таблица) — узнаем, что ПО пишет/читает
   и что возвращает прошивка.
3. **Трассировать вызов 29CD744C**: посмотреть в sm2lib.dll/plxlib.dll, откуда берётся
   код (вычисление из ответа адаптера).

## 6. Хронология/доказательства

- `firmware.bin` — полный дамп 256KB с адаптера (2.22.3 после OTA):
  bootloader ID 0x0A111788 (= 2.21.32-эпоха, не обновляется) + новый stage2 + новое
  приложение с VT.
- RAM-дамп `core_entry.bin` снят с работающего адаптера: state bootloader = 3
  (приложение работает), флаг stage2 = 2 (запуск приложения), PC=0x0800C15C (VM-функция F).
- hang-тесты A/B (RAM при connect-under-reset): PC=0x0800032C (reset handler) —
  J-Link останавливал ядро под reset; RAM содержит следы работавшего приложения.
- Все строки версии 2.22.3/2.21.35 в прошивке отсутствуют (версия живёт в EEPROM-регистрах
  и передаётся ПО по протоколу).
