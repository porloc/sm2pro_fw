# SM2 Pro (Scanmatik-2 clone) — восстановление и сборка прошивки

Реверс-инжиниринг и восстановление noname J2534 pass-thru адаптера **SM2 Pro**
(клон Scanmatik-2, контроллер **STM32F105VCT6**, 256 КБ flash) из состояния
«битый дамп» в полностью рабочее. Плюс извлечение более новой прошивки
**2.22.3** из дистрибутива ПК-программы и перенос на неё «патча клона».

## Содержимое

| Путь | Описание |
|------|----------|
| `firmware/` | Готовые образы прошивки (полный флеш 256 КБ и компоненты), включая **эталон отката `fw_22135.bin`** |
| `docs/` | Подробные отчёты: бутлоадер, шифрование, патчи, ошибки [0007]/00000, **разборы захватов API Monitor и USBPcap** |
| `captures/` | Сырые захваты обмена ПК↔прибор: API Monitor (эталон 2.21.35 и клон 2.22.3), USBPcap-логи |
| `scripts/` | Скрипты анализа и сборки (Python + capstone) |

Не включены (тяжёлое и избыточное): установщики дистрибутивов Scanmatik
2.21.32 / 2.22.3 / prog_22135.exe (34–42 МБ), распакованные содержимые
дистрибутивов и драйверов, проект Ghidra. В репозитории — только результаты
анализа: документация, прошивки, скрипты сборки и сырые захваты.

## Какой файл прошивать

**`firmware/SM2Pro_full_flash_2.22.3_patched_v2.bin`** — основной рекомендованный
образ: бутлоадер 2.21.32 (донорский) + stub 2.22.3 + приложение 2.22.3 с патчем
клона (чтение UID из EEPROM, как у рабочего донора) + корректные данные EEPROM
(слоты идентификации запуска и загрузочная запись 2.22.3). Именно v2 исправляет
ошибку **[0007] Внутренняя ошибка микропрограммы адаптера (FLASH/MCU)**,
возникающую с первой версией образа — см. `docs/ERROR_0007_ANALYSIS.md`.

### Статус: лестница тестов ПРОЙДЕНА — приложение 2.22.3 живо, виновник локализован

Три диагностические прошивки испытаны под API Monitor (разбор — **`docs/APIMON3_LADDER_ANALYSIS.md`**, захваты в `captures/apimon3_ladder/`):

| # | Тест | Результат на экране | Что доказано |
|---|---|---|---|
| 1 | PROBE (стаб-резидент) | «00000» | **стаб ответил на AUTH статусом 1 за 0,5 мс** — транспорт после LAUNCH идеален; «00000» = реакция ПК на любой невалидный исход AUTH |
| 2 | AUTH_BYPASS (обход крипто-ядра) | **другая ошибка** | **приложение 2.22.3 ответило на AUTH (64 Б, статус 0)** — главный цикл/диспетчер/отправка работают; ПК принял ответ и отправил верификацию 248 Б (серийник + ключ блоба донора); через ~0,6 с приложение умерло полностью (USB исчез) — причина смерти не AUTH-обработчик |
| 3 | MODE1 (поколение платы 1) | «00000» | до байта совпадает с patched_v2 — гипотеза поколения платы снята |

**Итог: зависание — внутри обфусцированного крипто-ядра 0x0800C15C** (единственный VM-интерпретатор в приложении, 147 обработчиков на диспетчере 0x0800C2CA, единственный вызов — из AUTH-обработчика). Реверс ядра показал: ни svc, ни периферии, ни чтений аппаратного UID (все 9 пулов пропатчены), входы согласованы (серийник+ключи+виртуальный UID донора) — статически «всё должно работать». Рабочая гипотеза: **ядро рассчитано на новое поколение бутлоадера** (записи обновления 2.22.3 бутлоадер не пишут; оба известных серийника старого поколения — в чёрном списке из 27). Смерть после AUTH в тесте 2 — отдельная точка (пост-AUTH init железа J2534 или обработка 248 Б), не крипто.

**Следующий шаг — решающий эксперимент: дамп зависания по SWD** (ST-Link или J-Link OB — см. ниже раздел «Дамп зависания по SWD»): остановить зависшее ядро и увидеть точный PC. Полный гайд под J-Link OB (Blue Pill) — **`docs/JLINK_OB_GUIDE.md`**.

#### Прошлая стадия (захват №2, для истории)

Прошит `patched_v2`, под API Monitor снята сессия smwin 2.22.3 (15,15 с,
3 одинаковых цикла). Транспорт и цепочка запуска работают **идеально**,
отказ ровно один — см. **`docs/APIMON2_ANALYSIS.md`**:

* `0x83 INFO` → прибор честно отвечает версию **0x1198** (EEPROM-фикс v2
  работает, ошибка [0007] мёртв; серийный донора A111788 в чёрном списке
  ПО не мешает — версия совпала, путь обновления не запускается);
* `0x88 ARM` → OK; `0x37 LAUNCH` {ver=0x1198, crc=0x210E9A13, size=0x1353C}
  → OK — сверки EEPROM-слотов 3–8 пройдены, **приложение запущено**;
* `0x12 AUTH` (новый формат: challenge 172 Б вместо 10 Б) → **прибор молчит
  ~1,4 с → драйвер возвращает ERROR_GEN_FAILURE** — это и есть экранная
  «Внутренняя ошибка микропрограммы 00000».

Приложение 2.22.3 не имеет своего USB-стека — связь идёт через сервисы
бутлоадера (0=приём, 1=отправка, 3=тик, 13=регистрация), как у стаба,
который на том же бутлоадере работает; USB — поллинговый OTG_FS,
прерывания не используются.

**Эталон отката:** `firmware/fw_22135.bin` — побайтовый дамп РАБОЧЕГО состояния
этой же платы на 2.21.35 (серийник A71283, виртуальный UID в EEPROM,
патч-слово 0x0800EB50). При любых проблемах — залить по 0x08000000, прибор
гарантированно возвращается в рабочее состояние (проверено).

**Контрольный тест железа:** `SM2Pro_full_flash_2.21.32_donor_asis.bin` +
**СТАРОЕ ПО 2.21.32** (его sm2lib.dll 451 584 байта ждёт версию 0x1070 и не
содержит A111788 в списке «не обновлять») — единственная гарантированно
рабочая пара «прошивка+ПО».

Альтернативы:
* `SM2Pro_full_flash_2.22.3_official_v2.bin` — «как настоящий прибор»
  (приложение без патча UID, EEPROM исправлен);
* `SM2Pro_full_flash_2.22.3_patched_v2_slots_only.bin` — патч клона, исправлены
  только слоты запуска (загрузочная запись осталась 2.21.32 — тоже работает);
* `SM2Pro_full_flash_2.21.32_donor_asis.bin` — точная реконструкция донорского
  дампа 2.21.32 (рабочая, под ПК-программу 2.21.32);
* `SM2Pro_full_flash_2.21.32_restored.bin` — то же, но с официальным чтением UID.

Использовать с ПК-программой **Scanmatik 2.22.3** (тот же дистрибутив, из
которого извлечена прошивка).

## Прошивка (SWD, ST-Link/J-Link/OpenOCD)

1. Подключение: SWDIO=PA13 (нога 72 LQFP100), SWCLK=PA14 (нога 76), GND, 3V3
   (только измерение VTref; прибор питается от своего USB).
2. Если включена readout-защита (RDP) — снять: Option Bytes → RDP = 0xAA
   (при этом флеш сотрётся — это нормально).
3. Залить полный образ по адресу **0x08000000**:

```bash
# ST-Link + openocd
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg \
        -c "init; reset halt; flash write_image erase SM2Pro_full_flash_2.22.3_patched_v2.bin 0x08000000; reset run; exit"
# или
st-flash --format binary write SM2Pro_full_flash_2.22.3_patched_v2.bin 0x08000000

# J-Link OB (Blue Pill): файл flash.jlink с содержимым
#   loadfile SM2Pro_full_flash_2.22.3_patched_v2.bin,0x08000000
#   r
#   g
#   qc
JLink.exe -device STM32F105VC -if SWD -speed 4000 -AutoConnect 1 -CommanderScript flash.jlink
```

4. Питание перезапустить, подключить ПК-программу Scanmatik 2.22.3.
   ВАЖНО для J-Link: `r` и `g` после loadfile обязательны — без них ядро
   остаётся остановленным и прибор выглядит «мёртвым» до перетыка питания.
   Подробно (распиновка, J-Flash Lite, проверка связи) — `docs/JLINK_OB_GUIDE.md`.

## Дамп зависания по SWD (решающий эксперимент; ST-Link или J-Link OB)

Прибор зависает и ОСТАЁТСЯ живым под SWD — ядро можно остановить и увидеть
точное место зависания (PC). Два прогона:

* **Прогон A (крипто-ядро):** прошить `SM2Pro_full_flash_2.22.3_patched_v2.bin`,
  запустить smwin 2.22.3, дождаться «00000»;
* **Прогон B (смерть после AUTH):** прошить
  `SM2Pro_full_flash_2.22.3_AUTH_BYPASS.bin`, дождаться ошибки (≠ 00000) и
  сфотографировать её код (таблица кодов 0–21 — в sm2ptconfig.exe; точный код
  теста №2 пока не зафиксирован — ссылка «скриншот» с Drive оказалась ещё
  одной копией .apmx86-лога AUTH_BYPASS).

В обоих: **не выключая питание и не переткнувая USB**, выполнить дамп:

```bash
# ST-Link + openocd
openocd -f interface/stlink.cfg -f target/stm32f1x.cfg -f scripts/dump_hang.cfg

# J-Link OB (Blue Pill); итог: hang_dump_log.txt + hang_ram.bin
JLink.exe -device STM32F105VC -if SWD -speed 1000 -AutoConnect 1 -CommanderScript scripts/dump_hang.jlink
```

Скрипты выводят регистры ядра (pc/sp/lr), регистры отказов (CFSR/HFSR),
скретч и таблицу VM крипто-ядра, окно стека; J-Link-вариант дополнительно
сохраняет полный дамп RAM 64 КБ (hang_ram.bin). Интерпретация:
* pc в 0x0800C15C-0x0800CED4 → вечный цикл VM (таблицу расшифруем офлайн);
* pc на обработчике отказа приложения (HardFault 0x08015CE4,
  BusFault 0x080142D8, NMI 0x0800892C, UsageFault 0x08009280) → fault
  (регистры отказов укажут команду);
* pc в init-коде → проблема железа клона.

Бонус-прогон с брейкпоинтами (вход в ядро 0x0800C15C, возврат 0x08007292,
fault-вектора) — в `docs/JLINK_OB_GUIDE.md`, раздел 6.

## Архитектура загрузки (главные выводы реверса)

1. **Бутлоадер** (0x08000000) держит USB-стек, драйверы flash/EEPROM,
   криптографию и таблицу из 14 сервисов [0x0800017C]. Приложение и stub
   вызываются как подпрограммы и пользуются этими сервисами (приём/передача
   сообщений, CRC, EEPROM-слоты). Команды 0x80–0x89 обслуживает бутлоадер,
   остальные сообщения передаются запущенному коду (state 3 = passthrough).
2. **Запуск цепочки**: ПК → 0x83 INFO (версия из загрузочной записи EEPROM) →
   0x88 ARM → бутлоадер запускает код по 0x08004000 (в 2.22.3 это stub) →
   ПК → 0x37 LAUNCH {ver, crc, size} → stub сверяет слова с EEPROM-слотами
   3–8 и запускает приложение по 0x08005000.
3. **EEPROM-слоты**: адрес слота N = 0x08002800 + (N+0x40)·2, активная
   страница — по маркеру 0x5AA5 в конце страницы. Запись слотов 3–8
   выполняет только штатное обновление (команда 0x35 stub'а).
4. **Прошивка шифруется** поточным шифром (K1=0x13AB3377, K2=0x5188016B,
   A=0xCAFE1381, B=seed 0x7821AB35) и хранится в `sm2lib.dll` ПК-программы;
   параметры — имmediates в функции заполнения записей обновления
   (2.22.3 — VA 0x1000C760). CRC — стандартный zlib CRC-32.
5. **Патч клона**: все точки чтения аппаратного UID 0x1FFFF7E8 (в 2.21.32 —
   одно слово 0x0800E958, в 2.22.3 — девять слов в пулах литералов)
   перенаправлены на «виртуальный UID» в EEPROM (0x080028E8) — устройство
   сообщает ПК отпечаток донорского прибора.
6. **Список серийников «не обновлять»**: sm2lib.dll 2.22.3 содержит 27
   обфусцированных (XOR 0x33335555) серийных номеров, для которых обновление
   прошивки пропускается. Серийник донора **A111788 входит в этот список** —
   поэтому ПК-программа не перезаписывает патченное приложение, но и не
   заполняет EEPROM-слоты автоматически (их должен содержать образ).

## Скрипты

* `scripts/parse_apmx86.py` — парсер захватов API Monitor (.apmx86): хронология

## Снятие логов обмена (закрыто: API Monitor решает всё)

**USBPcap больше не нужен** (см. `docs/APIMON2_ANALYSIS.md`, раздел «USBPcap:
закрыть вопрос»): на этой машине он не даёт bulk-пакетов при живом обмене, а
подключение фильтров ломает привязку smndis. API Monitor покрывает протокол
полностью — обе сессии (эталон и клон) расшифрованы до байтов.

Инструкция для истории: прибор — vendor-USB (VID **0x20A2:0001**, 2 bulk-эндпоинта
64 байта: 0x81 IN / 0x02 OUT), **не COM-порт** — COM-сниферы не подходят.
Снималось связкой Wireshark + USBPcap (пошаговая инструкция в
`docs/CAPTURE_LOGS.md`). Готовый парсер логов: `scripts/parse_usbpcap.py`.
Ранние захваты — в `captures/usbpcap_user_00000/` и `captures/usbpcap_22135_working/`.

## Анализ первого снятого лога (v1, USBPcap)

Захват прошивки v1-образа (51,5 с, 29636 пакетов) разобран полностью —
результат в `docs/LOG1_ANALYSIS.md`. Главное: **за всю запись ПК не отправил
адаптеру ни одного байта** (только перечисление в t=0, дальше тишина; обмен
других устройств шины при этом виден). Значит ошибка вида [0007]/00000 может
выдаваться программой ещё до начала обмена с прибором. Bootloader при этом
жив и стабилен (корректные дескрипторы, ни одного disconnect за 51 с).
Дальше: строгий порядок записи (старт захвата → переткнуть адаптер → запуск
программы → ошибка → стоп) и «золотой» захват donor 2.21.32 + старое ПО.

## Анализ лога №2 + скриншота: вероятная ПРИЧИНА всех «00000» (найдена)

Разбор второго захвата (28,5 с) и реверс sm2lib.dll / smndis.sys /
sm2ptconfig.exe выявил полную цепочку обнаружения прибора на ПК —
см. `docs/LOG2_ANALYSIS.md`. Кратко:

* sm2lib находит адаптер **только по имени сетевого подключения**
  `DIRECT-SCANMATIK-#XXXXX` (перечисление через `GetIfTable`, парсинг
  hex-числа после `#`); затем открывает `\\.\SmUsb000…009`;
* имя подключения ставит **только фирменный софт** (sm2ptconfig и др.,
  формат `DIRECT-SCANMATIK-#%05X`), **с правами администратора**; INF и
  драйвер сами имя не создают;
* при смене USB-порта/переустановке Windows создаёт **новый экземпляр
  адаптера с именем по умолчанию** — фирменное имя слетает, прибор становится
  невидим для программы → ни одного пакета на USB → таймаут «00000»;
* у пользователя сейчас адаптер — **экземпляр №3** («Scanmatik USB-NDIS #3»)
  после переноса из хаба в прямой порт → имя почти наверняка сброшено.
  Это объясняет, почему v2/PROBE/MODE1 и даже донорский образ дали
  одинаковые 00000 — **до прибора обмен не доходил**.

Проверка: `ncpa.cpl` → имя подключения Scanmatik (ожидается
`DIRECT-SCANMATIK-#…`). Лечение: sm2ptconfig.exe **от администратора**.

## Итог: прибор восстановлен на 2.21.35 (анализ рабочего комплекта)

Прошивка 2.21.35 с родной программой работает. Разбор рабочего дампа,
прошивки из драйвера и нового лога USB — в [docs/WORKING_22135_ANALYSIS.md](docs/WORKING_22135_ANALYSIS.md). Коротко:

- **Дамп = официальная прошивка из sm2lib.dll 2.21.35 + ровно одно
  патченное слово** (0x0800EB50: чтение UID кристалла 0x1FFFF7E8
  перенаправлено на «виртуальный UID» в EEPROM 0x080028E8 — тот же
  патч клона, что в доноре 2.21.32, только с новой обфускацией
  +0x33333333) + бутлоадер + метаданные `{crc,ver,size}` на 0x08002800
  (совпадают с дескриптором драйвера до бита) + индивидуальные данные
  EEPROM/хвоста.
- **Разгадана ошибка [0007]**: в образе v1 метаданные на 0x08002800
  остались от донора 2.21.32, а стаб+приложение были 2.22.3 — команда
  LAUNCH сверяет EEPROM-идентификацию с прошивкой и отвечает статусом 7.
- **Серийник рабочего дампа 0x00A71283 тоже в чёрном списке ПО 2.22.3**
  (как и донорский A111788) — обновляться программой 2.22.3 бессмысленно.
- Лог USB (третий захват): у адаптера снова 0 пакетов — обмен в окно
  записи не попал; фиксируется только SCSI-опрос флешки. Инструкция,
  как снять лог правильно, — в отчёте.
- Рекомендация: оставаться на 2.21.35 и не запускать обновление прошивки.

## API Monitor: протокол расшифрован полностью, диагноз 2.22.3 поставлен

USBPcap оказался бесполезен на этой машине (0 bulk-пакетов при живом обмене,
фильтры ломают привязку smndis). Вместо него ПО мониторилось **API Monitor x86**
(хуки CreateFileW / DeviceIoControl / CloseHandle / GetIfTable). Бинарный формат
.apmx86 разобран полностью (ZIP: definitions + process/0/{info,calls,data};
ключ — поле @36 записи вызова = указатель на API в базе определений).
Оба захвата — в `captures/`.

**Захват №1 — эталон нормы** (`captures/apimon1_22135_working/`, 97 вызовов,
11,7 с): рабочий комплект 2.21.35. Хендшейк: `0x83 INFO` → {серийный 0x00A71283,
версия 0x1096}; `0x88 ARM` → OK; `0x12 AUTH` (challenge 10 Б) → ответ 100 Б, в
хвосте — байты виртуального UID `52 59` (клон-патч работает, ПО принимает
прибор); дальше — рабочий цикл опроса статуса с адаптивным интервалом
(backoff 138…5212 мс). Команд обновления (0x80–0x82) в сессии нет. Реконструкция
протокола по реверсу подтверждена до байта. Разбор — `docs/APIMON_CAPTURE_ANALYSIS.md`.

**Захват №2 — клон на 2.22.3** (`captures/apimon2_2223_patched_v2/`, 44 вызова,
15,15 с, 3 идентичных цикла): INFO/ARM/LAUNCH — все OK (EEPROM-фикс v2 работает,
приложение запущено), отказ ровно один — **приложение 2.22.3 молчит на AUTH**
(challenge 172 Б, новый формат), через ~1,4 с драйвер возвращает
ERROR_GEN_FAILURE → экранная «00000». Статический разбор обработчика AUTH
0x0800722C: проверка длины 0xAC, svc 7 (серийный), svc 8 ×2 (ключи), вызов
обфусцированного крипто-ядра 0x0800C15C, `cbz r0` → ответ / статус 6. Все входы
ядра (крипто-блоб 0x08000184, виртуальный UID 0x080028E8) донорские и на месте →
либо диспетчер приложения не доходит до 0x12 (смерть на init), либо зависает
само ядро. Разбор — `docs/APIMON2_ANALYSIS.md`.

Следующий шаг — лестница проб: **PROBE → AUTH_BYPASS → MODE1** (таблица выше,
в разделе «Какой файл прошивать»). Интерпретация каждого результата — в
`docs/APIMON2_ANALYSIS.md` и `docs/DIAGNOSTIC_PLAN_v2.md`.

## Предупреждения

* Не запускать штатное «обновление прошивки» в ПК-программе на приборе с
  патченным приложением и серийником не из списка «не обновлять» — официальная
  прошивка затрёт патч (устройство останется рабочим, но вернётся к чтению
  аппаратного UID).
* Все действия — на свой риск.
